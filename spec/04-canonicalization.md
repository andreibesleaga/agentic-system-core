# AGSC-04 — Canonicalization and determinism

## 4.1 The determinism obligation

- **AGSC-04-01** Two builds of the same Bundle content with the same `SOURCE_DATE_EPOCH` MUST produce byte-identical output on every operating system and every runtime. [PRD-004 ← R32, Art. XII]
- **AGSC-04-02** Verification is a double build into two directories followed by a recursive byte comparison; any difference is error `AGSC-E602`. [PRD-004]
- **AGSC-04-03** A build MUST NOT read a wall clock, resolve the network, read environment locale, or depend on filesystem enumeration order. [Art. XII, C9]

## 4.2 JSON (JCS, RFC 8785)

- **AGSC-04-04** Every emitted JSON artefact — `graph.jsonld`, per-item `.jsonld`, `search.json`, the well-known file, `dist/gate.json`, `ledger.jsonl` entries — MUST be JCS-canonical and MUST be followed by exactly one LF. Vector files are **not** emitted artefacts: they are governed by AGSC-09-06, which requires JCS member *order* but permits pretty-printing. This rule binds at **Level 2 and above** (AGSC-10-04). A Level-0 publisher's JSON artefacts MUST be valid I-JSON (RFC 7493) and SHOULD be JCS-canonical, and `tools/validate-wellknown --level 0` MUST NOT require canonical bytes — UTF-16 member ordering and ECMA-262 number formatting are not something a CMS export produces by accident, and Level 0 exists precisely so that it need not. [research/12 §P rule 19, D48(7) ← V5-3 S3-04, AGSC-10-02]
- **AGSC-04-05** JCS here means: UTF-8 output; no whitespace between tokens; members sorted by **UTF-16 code units** of the member name; numbers per ECMA-262 §7.1.12.1 (`Number#toString`); input restricted to I-JSON. Locale and Unicode code-point sorting MUST NOT be used: they differ from UTF-16 order for astral-plane keys. A number MUST NOT serialise as `-0`: ECMA-262 §7.1.12.1 renders negative zero as `0`, so a producer emits `0`. *(amended at rc.5, V9A-19: the earlier sentence cited RFC 8785 erratum 7920 as its authority. That erratum — Verified, reported 2024-05-02 — in fact recommends the opposite remedy, "a JSON parser following this specification SHOULD generate an error condition … when it encounters -0"; it notes that the serialisation is lossy and addresses the **parser**. This specification chooses the producer-side rule instead, because I-JSON input is a precondition of AGSC-04-05 and a Bundle never authors `-0`.)* **The UTF-16 rule governs JSON member names and nothing else** — every other ordering in this specification is code-point (AGSC-04-12/13), and the two differ only for astral-plane text, which reaches member names through `search.json` tokens (AGSC-06-23) and nowhere else. A port MUST therefore sort member names by UTF-16 code units (comparing surrogate-aware, not by rune) even where its language's default string order is by code point; vector `jcs-0003` proves it. [research/12 §P rule 24 as corrected; audit/G §1 RFC 8785 row]
- **AGSC-04-06** A JSON artefact that is not JCS-canonical is error `AGSC-E601`. [PRD-004]

## 4.3 Text

- **AGSC-04-07** All emitted text MUST be UTF-8 without BOM, LF-terminated, NFC-normalized, with exactly one trailing LF. Non-NFC output is `AGSC-E604`. [research/12 §P rule 1, §3]
- **AGSC-04-08** Slugs, keys and IRIs stay ASCII; titles, descriptions and aliases MAY be any Unicode in NFC. [research/12 §P rule 39]

## 4.4 Time

- **AGSC-04-09** The build instant MUST come from `SOURCE_DATE_EPOCH` (integer seconds since the Unix epoch), defaulting to the last commit time. Where no git history exists — the drop-in flow of PRD-053 runs before `git init` — the default MUST be `0` (`1970-01-01T00:00:00Z`) with warning `AGSC-E606`, so the instant is always defined. A malformed value MUST exit 2 (`AGSC-E603`, the configuration class of AGSC-09-08); the variable MUST NOT be unset for child processes. [research/12 §3, §P rule 23; D48(7)]
- **AGSC-04-10** Every embedded timestamp MUST be rendered from that instant as `YYYY-MM-DDTHH:MM:SSZ` — UTC, seconds precision, never milliseconds, never a local offset. [research/12 §P rules 7, 23]
- **AGSC-04-11** Staleness, "last build" and NOW counts MUST all derive from the same instant (amended at rc.5, R-15: "feed dates" removed with `/feed.xml`). Only the `refresh` verb MAY read a real clock, and a clock it reads MUST NOT reach any emitted artefact: ledger `ts` values derive from the committer times of the git-log file (AGSC-08-20a) and from `SOURCE_DATE_EPOCH` for the single trailing `build` entry, never from a wall clock, so a `refresh` observation can only open an issue. [PRD-015, PRD-017, G17, D48(7)]

## 4.5 Ordering

- **AGSC-04-12** All ordering — except the JSON member-name ordering of AGSC-04-05, which is UTF-16 code units by deliberate exception (V6-B U3) — MUST be code-point comparison of the sort key. Locale collation, case-insensitive collation and `Intl` comparators MUST NOT be used. [research/12 §P rule 24]
- **AGSC-04-13** Explicit sort keys: items by slug; links by `(key, target)`; tags by code point; cluster members by `(order, slug)` with absent `order` sorting last; search tokens as JSON member names per AGSC-04-05 (UTF-16 code units), never by code point; sitemap entries by URL; N-Quads lines by their serialized bytes; RDF subjects, then predicates, then objects by IRI or lexical form; JSON object members by AGSC-04-05. [research/12 §3, §P rule 24]
- **AGSC-04-14** Arrays authored by a human (`tags`, `clusters`, `aliases`, Link arrays) MUST retain author order in the source file and MUST be sorted only in derived artefacts, so that `lint --fix` never reorders meaning-bearing first entries such as the primary cluster. [audit/D §1.2]

## 4.6 Hashes and the canonical RDF form

- **AGSC-04-15** `graph.nq` — canonical N-Quads, code-point ordered, each quad terminated by a single LF — is the hashed form of the graph. `bundle.hash` MUST be the lowercase hex SHA-256 of its bytes. [research/12 §P rule 21]
- **AGSC-04-16** Because exports are blank-node-free (§05), RDFC-1.0 canonicalization degenerates to this sort. An implementation MUST scope any conformance claim to "canonical N-Quads equal to RDFC-1.0 output for blank-node-free datasets" and MUST NOT claim full RDFC-1.0. [D41, audit/G §1 RDFC row]
- **AGSC-04-17** Content hashes elsewhere (per-item Markdown, ontology files, skill packs) MUST be lowercase hex SHA-256 over the canonical bytes. A CIDv1 (`raw`, sha2-256, base32 `b…`) MAY additionally be emitted for `graph.nq`; when emitted it MUST be computed over the same canonical bytes. [research/12 §P rule 25]
- **AGSC-04-18** (amended at rc.5, R-15: `feed.xml` removed, because no 1.0 rule pins its bytes and AGSC-06-01 no longer emits it) `search.json`, `sitemap.xml` and the well-known file MUST be reproducible from `content/`, `agsc.config.json` (every URL derives from `site.base`, every switch from `build{}`) and `SOURCE_DATE_EPOCH`, plus — for the well-known file's `agsc-ledger-head` attribute alone — the git-log file of AGSC-08-02/08-20a. No other input exists — four inputs in all (V6-B U7). [research/12 §P rule 26, V3-05]

## 4.7 Normalization on write

- **AGSC-04-19** `lint --fix` MUST be idempotent: applying it twice MUST produce the same bytes as applying it once. Its normalizations are limited to line endings, NFC, trailing newline, frontmatter key order (**schema order** = the top-level `properties` order of `schema/item.schema.json`, then the matching `oneOf` branch's `properties` order, then unknown keys in code-point order — including inside a nested mapping, where the order is that `$def`'s `properties` order — the order AGSC-02-90 emits, so `lint --fix` never rewrites an adopted file), and wikilink rewriting. The emitted YAML profile is fixed: block style only, two-space indentation, sequence items indented two spaces under their key, plain scalars unless the value would re-parse as another type or begins with an indicator character (then double-quoted with `\` and `"` escapes only), one space after every `:`, no document markers, no trailing spaces. What it changed — and, where it only reports, what it would change — MUST be reported as a finding: a line-ending, BOM, NFC or trailing-newline normalisation under `AGSC-E108` (the encoding rule that obliges it, AGSC-01-14), every other normalisation of this rule under `AGSC-E506`. Both are warnings, so no exit code depends on the choice; without this sentence two conforming engines reported the same file under different codes *(added at rc.5, ENG2-03: four rules oblige `lint --fix` and no rule said which registered code its report carries)*. [PRD-003, AGSC-03-12]
- **AGSC-04-20** `lint --fix` MUST NOT change prose, reorder authored arrays, or add, remove or infer any key. [D43(1), Art. XIII]

## 4.8 Normalization order, Unicode version and the cross-implementation obligation (added at rc.3, 2026-09-16 — D67 B3, D72 A-06/A-20)

- **AGSC-04-21** **Order.** Normalization and canonicalization do not commute, so the order is fixed: text is NFC-normalized **first** (AGSC-04-07), then canonicalized (AGSC-04-05). Every JSON member name MUST be NFC-normalized **before** it is sorted; a producer that sorts first and normalizes afterwards emits different bytes for the same input and is non-conforming. The same order governs every derived artefact: normalize, then sort, then serialize. [D67 B3, SO-30a, V6-A VA-07]
- **AGSC-04-22** **Unicode version.** The vectors of `tests/vectors/**` were generated against **Unicode 16.0.0**; NFC, the General_Category classes of the tokenizer (AGSC-06-23) and the case mapping of AGSC-03-13 are those of that version. The vector set is version-stable: every character in it has identical NFC, General_Category and case-mapping properties from Unicode 15.0 through 18.0.0 (verified 2026-09-17 by V7's recomputation and the Unicode stability policy), so a runtime on any of those versions passes the set and the pin names the generation version, not a runtime requirement (AR2-36). A conforming implementation MUST state the Unicode version of its runtime in its conformance claim (AGSC-09-01). A divergence that arises only from a different Unicode version, on input outside the vector set, is a documented divergence and not a conformance failure; a divergence **on the vector set** is a failure. [D72 A-06/C19]
- **AGSC-04-23** **Combining-sequence bound.** NFC is computed per starter-delimited segment, so a segment must be buffered before any of it is emitted. A conforming implementation MUST NOT buffer without bound: a starter followed by more than **256** combining marks is `AGSC-E607` (a lint error naming the file and offset), never a silent truncation and never unbounded memory. [D72 A-20]
- **AGSC-04-24** **Cross-implementation obligation.** Byte-identity across *implementations* is claimed for the machine artefacts — `graph.jsonld`, `graph.ttl`, `graph.nq`, per-item `.jsonld`, `search.json` and its shards, `chunks.jsonl` and its shards, `ledger.jsonl`, `/.well-known/knowledge-linkset`, `/llms.txt`, `/llms-full.txt` and the board exports — and is discharged by the expected-byte vectors that name them. The seven Harness **file kinds** of AGSC-07-12 carry the same obligation, discharged when the `harness/` vector area is populated; until then no conformance claim may assert cross-implementation byte-identity for a Harness. *(amended at rc.5, V8-101: the earlier text named "the seven Harness files" as already discharged, while `tests/vectors/harness/` is a declared-but-empty area and the two `compose/` vectors assert `harness_emitted: false` only; AGSC-07-12 also defines seven file **kinds**, two of them one file per selected item, so "seven files" was never literally seven.)* Generated **HTML** is byte-identical within one implementation (AGSC-04-01) and is NOT part of the cross-implementation vector set: no rule pins a Markdown renderer's output. A conformance claim MUST NOT assert cross-implementation byte-identity for HTML. [D67 B3, D72 C1/A-12, PRD-060]
