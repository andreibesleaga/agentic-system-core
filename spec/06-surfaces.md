# AGSC-06 — Published surfaces: routes, discovery files, llms.txt

## 6.1 Route set

- **AGSC-06-01** A writer MUST emit exactly this route set into `build.out` (default `www/`): `/`; `/concepts/` and `/concepts/<slug>/`, plus `/<type-plural>/<slug>/<lang>/` for every language variant (AGSC-01-13, reserved to 1.1 — none at 1.0); `/procedures/`, `/lessons/`, `/episodes/`, `/gates/` with their item pages; `/clusters/` and `/clusters/<slug>/`; `/tags/<tag>/`; `/search/` with `/search.json`, plus `/search-<nn>.json` shards and `/<route>/page-<n>/` index pages above the bounds of AGSC-06-21; `/now/` and `/now.md`; `/compose/`; `/skills/`, `/skills/index.json`, `/skills/<cluster>/SKILL.md`; `/specs/` and `/specs/agentic-knowledge/`, plus `/specs/mcp/` when the `mcp` surface is declared (AGSC-11-16) (the published specification of the AGSC-06-07 profile URI, the 303 target of the w3id `profile/agentic-knowledge` rule, which MUST carry an anchor `#link-relations` and one anchor **named exactly as the fragment of the relation URI** — `#graph`, `#ontology`, `#context`, `#now`, `#skills`, `#ledger`, `#peer`, `#surface`, `#contribute`, `#access`, `#signature`, `#boards` — per AGSC-06-10 extension relation, so that a client that does follow an extension relation URI lands on that relation's documentation; RFC 8288 §2.1.2 permits that but discourages it, saying "clients SHOULD NOT automatically access that resource to avoid overburdening its server"); `/ns/context.jsonld` and `/ns/<ontology-version>/context.jsonld` (AGSC-06-32, AGSC-05-09), which are the only `/ns/` routes a content node emits — the vocabulary documents `/ns/agsc.ttl`, `/ns/agsc.rdf` and the `/ns/` HTML index, and the three JSON Schemas at their `$id` URLs `/ns/schema/{bundle,config,item}.schema.json` (so that each `$id` resolves), are published by the namespace document site alone, which is what the w3id negotiation of AGSC-06-06 resolves to; `/about/`; `/legal/`; `/changelog/`; `/graph.jsonld`, `/graph.ttl` and `/graph.nq`; `/pages/<slug>.md` and `/pages/<slug>.jsonld`; `/attachments/<slug>/<file>` for every attachment an item names (AGSC-02-98; the served bytes are the hashed bytes of AGSC-05-29); `/assets/<path>` for every file under `content/assets/` that a published item's body references (AGSC-03-11), `<path>` being that file's path relative to `content/assets/` and the served bytes being the authored file's bytes *(AGSC-03-11 admits a body image or link into `content/assets/` and AGSC-02-95 creates such files during adoption, byte for byte; this route is what such a reference resolves to.)*; `/llms.txt` and `/llms-full.txt`; `/sitemap.xml`; `/robots.txt`; `/.well-known/tdmrep.json`; `/ledger.jsonl`; `/chunks.jsonl` and its `/chunks-<nn>.jsonl` shards (AGSC-06-26/31); `/boards/index.json`, `/boards/<cluster-slug>.json` and `/boards/<cluster-slug>/` (the human view of the same board) when the Bundle holds at least one task item (AGSC-10-13); optionally `/graph/fragments/**` with `/graph/fragments/index.json` (AGSC-06-33); `/.well-known/knowledge-linkset`; `/.well-known/security.txt`; `/404.html`; and, for the **Cloudflare Pages deployment profile**, `_headers` and `_redirects` (AGSC-06-17).

  A writer targeting another host MUST emit the equivalent configuration for that host and MUST state which deployment profile it emitted in its conformance claim (AGSC-09-01); the normative content is the header set of AGSC-06-17, AGSC-11-03 and AGSC-11-05 and the redirect of AGSC-06-17, never the file format. This route set bounds what a writer MUST emit; it is not a bound on every file that may sit in the deployed directory, and the same-origin script assets a page of this set loads — `/compose/` and every item page load them so that the page tools of AGSC-09-16 can be registered, and AGSC-06-17's `script-src 'self'` policy leaves a writer no inline alternative — are emitted as part of the page that names them and are not routes of their own. The same holds for the two presentation files every page of this set links, the stylesheet `/assets/site.css` and the theme-control script `/assets/theme.js` of AGSC-06-05: a Bundle that authors `content/assets/site.css` replaces the default stylesheet at that path whether or not a body references it, and `/assets/theme.js` is always the writer's own, and so is the one script the `/search/` page loads to search `/search.json` in the page, `/search/agsc-search.js`, which MUST tokenize a query exactly as AGSC-06-23 tokenizes an item — a writer that ships that page MUST emit the script as part of it. *(Rationale: `_headers` and `_redirects` are Cloudflare Pages configuration files whose grammar no rule pins, and holding a Level-2 writer on nginx, Apache, S3 + CloudFront or a Solid pod to them would make every Level-2 claim implicitly Cloudflare-shaped.)*

  `/ledger.jsonl` is the derived ledger of §08, published so that a reader can recompute the chain offline (AGSC-08-23) and so that the `rel#ledger` link of AGSC-06-10 has a target. `/search/` and `/search.json` are unconditional (AGSC-06-16 MUSTs the index). The conditional routes are the shards and index pages of AGSC-06-21/06-31 (by size), `/boards/**` (by the presence of a task), `/specs/mcp/` (only when the `mcp` surface is declared, AGSC-11-16), `/.well-known/agent-card.json` (only under AGSC-06-34), `/legal/` (only when the Bundle root carries a `LICENSE-CONTENT` file, AGSC-06-18), `/conformance/` (only when a claimant publishes the report AGSC-09-03 defines, which is a MAY), `/.well-known/void` (only when a publisher emits a VoID description independently, AGSC-06-12, which is a SHOULD-link and never an emission of this specification), `/.well-known/security.txt` (only when the Bundle root carries an authored `.well-known/security.txt` that states a `Contact:` field — AGSC-06-36), `/assets/<path>` (one route per authored asset file a published body references), `/specs/`, `/specs/agentic-knowledge/` and `/specs/mcp/` (only on the namespace document site the w3id rules of AGSC-06-06 resolve to; a content node links the specification there), `/about/` (only when the Bundle authors that page; its source and bytes are implementation-defined at 1.x), `/changelog/` and `/ledger.jsonl` (only when the build is given the git-log file of AGSC-08-20b; a Level-2 claim requires both, AGSC-10-04) and the optional `/graph/fragments/**` (AGSC-06-33); no other route is conditional. `/graph.rdf` and `/feed.xml` are **not emitted at 1.x**, and `build.rdfxml` and `build.feed` are reserved names rejected with `AGSC-E004` (`feed` is reserved because no 1.0 rule pins a feed's bytes, so the route cannot be derived and the switch has nothing to switch on).

  `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CITATION.cff`, `CONTRIBUTING.md`, `GOVERNANCE.md`, `CONTRIBUTOR-AGREEMENT` (AGSC-08-06) and the REUSE layout are repository files, not routes (PRD-047); only `security.txt` is published, at its RFC 9116 location above, and what it carries is AGSC-06-36's. [PRD-011]
- **AGSC-06-02** Item pages MUST link their own `/pages/<slug>.md` and `.jsonld`. An empty type folder MUST be omitted from navigation but MUST still resolve. [design]
- **AGSC-06-03** The site identity is software plus registry. A reading order, a "start here" sequence, chapter structure or companion framing MUST NOT be emitted. [design]
- **AGSC-06-04** `/404.html` and the host configuration of the writer's deployment profile — `_headers` and `_redirects` for Cloudflare Pages (AGSC-06-01) — MUST be generated, never hand-maintained; a renamed or superseded slug MUST produce a redirect entry in that configuration. [PRD-018, PRD-020]
- **AGSC-06-05** Pages MUST NOT reference a third-party origin, load a font, script or image from another host, set a cookie, use browser storage, or emit a beacon — with one exception: the theme control MAY keep the visitor's own theme choice in `localStorage` under the single key `agsc-theme`, whose only values are `light` and `dark`. It MUST write the key only when the visitor chooses a theme and remove it when the visitor chooses the system theme, MUST NOT read, write or send any other stored value, and every page MUST render and work when storage is empty or unavailable; the privacy section of `/legal/` (AGSC-06-18), where the node publishes one, SHOULD say that the choice is kept in the browser, is never sent, and is cleared with the site's data. *(Rationale: the theme control keeps one preference the visitor sets by an explicit choice; the value is never transmitted and identifies no one.)* [PRD-046]
- **AGSC-06-06** `/ns/` conneg is done by the w3id `.htaccess`, mapping `Accept` to a fixed table of same-origin static targets (`text/turtle` → `/ns/agsc.ttl`, `application/ld+json` → `/ns/context.jsonld`, `application/rdf+xml` → `/ns/agsc.rdf`, else the HTML index) — plus the legacy `Accept` aliases `application/x-turtle` (→ Turtle) and `application/json` (→ JSON-LD), which a node MAY accept and no node need send — plus one path rule that sends `/ns/<major>.<minor>.<patch>(/…)?` to the immutable versioned copy of that release before any term rule can capture it (`owl:versionIRI` must resolve). No project-owned server code exists; `/ns/<version>/…` copies are immutable, the pre-release copy `/ns/1.0.0-draft.1/` of AGSC-05-25 included. [ADR-005]

## 6.2 The well-known file

- **AGSC-06-07** There MUST be exactly one discovery file, `/.well-known/knowledge-linkset`, served as `application/linkset+json` carrying the RFC 9264 §5 profile parameter `profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"`. Where the hosting platform cannot carry a parameter on `Content-Type`, the node MUST instead send the response header `Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile"` (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served. Separate manifests MUST NOT be emitted; a release MAY carry a copy named `knowledge-linkset.json`. `agent-card.json` MUST NOT be published unless the node declares it as the `a2a-card` surface **and** declares a `responder` surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is `AGSC-E210`. The well-known suffix `knowledge-linkset` is **pending registration** under RFC 8615 through the Internet-Draft, and registration of the Profile URI is to be requested under RFC 7284 (First Come First Served); the discovery link uses the already-registered relation `describedby` (AGSC-06-25), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with `describedby` and the linkset media type — nothing in this specification says "registered" of the suffix or the profile before the registry does. **The suffix is a single point of substitution**: the reference implementation holds it as one constant (`WELLKNOWN_SUFFIX`) from which the `peers[]` schema pattern, the `_redirects` alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next candidate suffix by one MINOR and a regeneration: the new suffix is added and the present path keeps answering with a redirect to it, so no reader that knows only the present path breaks (AGSC-00-14) *(amended 2026-10-02 for 1.0.0: until `1.0.0-rc.6` this said "by one PATCH", but a new discovery address is an addition, which a MINOR makes)*. The profile URI carries no version: it names the same profile for every version of this specification with the same MAJOR, a discovery document states the version it follows in `agsc-spec-version` (AGSC-06-08), and a new MAJOR that changes what the profile fixes takes a new profile URI. [PRD-024, RFC 9264, RFC 9727 §7.3, RFC 6906]
- **AGSC-06-08** The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose **sole** top-level member is `linkset` (RFC 9264 §4.2.1); no other top-level member may be present; the `linkset` array holds exactly one link context object whose `anchor` is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05). Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link — a link whose row in the table below says *yes* under `digest` — MUST carry `digest` at Level 2 and above (AGSC-06-08a), a Dictionary with a single member whose key is the RFC 9530 algorithm name `sha-256` and whose value is an RFC 9651 §3.3.5 **Byte Sequence**, serialised per RFC 9651 §4.1 as `sha-256=:<base64>:` and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's `describedby` link to `graph.jsonld` and nowhere else: `agsc-spec-version` (one value), `agsc-generated-at` (one value, an AGSC-04-10 instant derived from `SOURCE_DATE_EPOCH`), `agsc-counts` (one `"<type-plural>=<n>"` string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30), `agsc-bundle-hash` (the AGSC-04 bundle hash, RFC 9530 syntax), and `agsc-bundle-version` (one value, the content version of AGSC-04-25: the hash says whether two nodes hold the same content and never what the publisher calls that content, so a reader that wants to cite or compare releases needs both). The ledger is the link `https://w3id.org/agentic-system-core/rel#ledger`, carrying `digest` and `agsc-ledger-head` (one value, the lowercase hex head of the derived ledger of §08). A node MAY carry one further link whose relation is `https://w3id.org/agentic-system-core/rel#signature` (AGSC-06-10) and whose target is a detached signature over the canonical bytes of this document. At 1.x no rule pins the signature format, no Level requires the link, it affects no digest, no claim and no walk, and a reader MUST ignore it if present. *(Non-normative: the digests of this rule establish that the bytes are the bytes the publisher hashed; they establish nothing about who the publisher is. The trust anchor at 1.x is the origin's TLS certificate and DNS name, and a publisher who needs more publishes the optional signature. The nearest comparator, the Agent2Agent Agent Card, makes a signature over its canonical card optional ("Agent Cards MAY be digitally signed", A2A §8.4, read 2026-09-16 and quoted in `docs/SECURITY-CONSIDERATIONS.md` §2); this specification keeps its own optional for the same reason and one more — a static node has no key custody — and the reasoning is written here rather than left to inference. No IANA-registered relation exists for a signature — the registry was read on 2026-09-23 and holds none — so the link can only take this specification's own extension-URI form, and AGSC-06-35's registered-names-only list cannot admit it.)* [PRD-024, RFC 9264, RFC 9530, RFC 9651] *(Amended 2026-10-02 for 1.0.0: the table below names every link the document carries, when, and which of them carry `digest`; until then "artefact link" was not defined.)*

  | Relation | Target | Present when | `digest` |
  |---|---|---|---|
  | `describedby` | `/graph.jsonld` | always | yes |
  | `alternate` | `/llms.txt` | always | yes |
  | `alternate` | the successor node's well-known URL (AGSC-11-23) | the node names a successor | no |
  | `license` | `/legal/` | the node serves that route | no |
  | `service-doc` | `/specs/` | the node serves that route | no |
  | `rel#graph` | `/graph.nq`, `/graph.ttl` | the node serves that route (one link per file) | yes |
  | `rel#context` | `/ns/context.jsonld` | the node serves that route | yes |
  | `rel#ontology` | `/ns/agsc.ttl` | the node serves that route (AGSC-06-10) | yes |
  | `rel#now` | `/now.md` | the node serves that route | yes |
  | `rel#skills` | `/skills/index.json` | the node serves that route | yes |
  | `rel#boards` | `/boards/index.json` | the Bundle holds a task (AGSC-10-13) | yes |
  | `rel#ledger` | `/ledger.jsonl` | Level 2 and above, and the node is not `restricted` | yes |
  | `rel#peer` | another node's well-known URL | one per `peers[]` entry (AGSC-10-12) | no |
  | `rel#surface` | a surface | one per surface served (AGSC-11-16) | no |
  | `rel#contribute` | a contribution endpoint | one per `contribute[]` entry (AGSC-11-14) | no |
  | `rel#access` | a credential page | the node is `restricted` and names one (AGSC-11-20) | no |
  | `rel#signature` | a detached signature | OPTIONAL, see above | no |
  | the relations of AGSC-06-35 | related systems | OPTIONAL | no |

  `rel#…` abbreviates `https://w3id.org/agentic-system-core/rel#…`. A `restricted` node carries `digest` only on the `describedby` and `/llms.txt` links (AGSC-11-20). A node MAY serve a further file under its own route; a link to it is not an artefact link of this table and carries no `digest` requirement. A surface link (`rel#surface`) carries no file digest: the `chunks` surface's records each carry their own `digest` (AGSC-06-29).

- **AGSC-06-08a** At **Level 0** (AGSC-10-02) the document is the **same** link set with every `digest` and every `agsc-*` attribute of AGSC-06-08 (`agsc-spec-version`, `agsc-generated-at`, `agsc-counts`, `agsc-bundle-hash`, `agsc-bundle-version` and `agsc-ledger-head`) omitted — the §11 attributes (`agsc-surface`, `agsc-surface-version`, `agsc-access`, `agsc-visibility`, `agsc-contribute-mode`, `agsc-tombstone`) are Level-independent — a CMS export has no ledger, no `graph.nq` and no build instant, and Level 0 does not ask for one. At Level 2 and above every `digest` REQUIRED by AGSC-06-08, and every `agsc-*` attribute on the `describedby` and `rel#ledger` links, MUST be present. There is no structural difference between the two: `linkset` is the sole member at every Level. [PRD-055]
- **AGSC-06-09** The `linkset` member MUST conform to RFC 9264: an array of link-context objects, each with `anchor` and relation-keyed arrays of objects carrying `href` and optionally `type`. A consumer that cannot obtain the discovery document at the well-known URL of AGSC-06-07 SHOULD try, in order, the home page's `describedby` link whose `type` is `application/linkset+json` (AGSC-06-25) — which names the copy a node MAY serve at a path it controls (AGSC-06-07) — and then `/llms.txt` (AGSC-06-13). This order is informative: a node is not obliged to be reachable by more than the well-known URL, and a reader that finds none of them reports `AGSC-E901`. *(Rationale: the well-known name is one door among several, and a consumer meeting a 404 needs a second door.)* [PRD-024, RFC 9264]
- **AGSC-06-10** Relation names MUST be either IANA-registered short names — the five this specification itself emits (`describedby`, `alternate`, `license`, `service-doc`, `author`) plus any relation AGSC-06-35 admits for a related-system link (`related`, `service-desc`, `service-meta`, `collection`, `item` and `cite-as`) — or extension URIs of the form `https://w3id.org/agentic-system-core/rel#<name>` with `<name>` ∈ `graph`, `ontology`, `context`, `now`, `skills`, `ledger`, `peer`, `surface`, `contribute`, `access`, `signature` and `boards` — of the first six, five have a route in AGSC-06-01 and `ontology` names the vocabulary document of the namespace document site (AGSC-06-06), which a content node does not serve: a node that does not serve it omits the link, and a node that does names its own copy; `peer` naming another node's well-known URL for the mutual-conformance test of AGSC-10-12; `surface`, `contribute` and `access` defined in AGSC-11-16, AGSC-11-14 and AGSC-11-20, whose targets are surfaces, contribution endpoints and credential pages and need not be routes of this node; `signature` defined in AGSC-06-08, whose target is a detached signature and need not be a route of this node *(the IANA link-relation registry holds no relation for a signature, so this specification's own extension form is the only one available)*; `boards` defined in AGSC-10-13, whose target is `/boards/index.json`. `shapes` is NOT a 1.x relation: SHACL shapes stay in the development lane (AGSC-05-24), so no `/ns/shapes.ttl` is published and a relation with no target would be a dangling promise. Unregistered short names MUST NOT be used. Extension **target attributes** (RFC 9264 §4.2.4.3) MUST use the prefix `agsc-` (`agsc-spec-version`, `agsc-generated-at`, `agsc-counts`, `agsc-bundle-hash`, `agsc-bundle-version`, `agsc-ledger-head`) so that they can never collide with the target attributes RFC 8288 §3.4 defines (`hreflang`, `media`, `title`, `title*`, `type`) or with those RFC 9264 §4.2.4 serialises — no registry of target attributes exists; `digest` is deliberately unprefixed: RFC 9530 supplies its algorithm token and RFC 9651 its value syntax, and the plain name keeps RFC 9727-style link-set consumers able to read it. Every extension target attribute value — `digest`, every `agsc-*` attribute, and `profile` where a related-system link carries it (AGSC-06-35) — is an array of strings (RFC 9264 §4.2.4.3); `type`, `title` and `media` are strings and `hreflang` is an array of strings (RFC 9264 §4.2.4.1). Within one relation's array, link objects are ordered by `href` (code point), and every `href` is absolute — the Bundle base plus the route. `type` values are advisory hints (RFC 9264 §4.2.4.1, "Target Attributes Defined by Web Linking", is where the `type` member is specified; RFC 8288 §3.4.1 is where the hint language is — "this is only a hint; for example, it does not override the Content-Type header field of a HTTP response obtained by actually following the link"); `application/jsonl` is used for `/ledger.jsonl` and is deliberately unregistered — a reader MUST NOT depend on it. [RFC 9264, RFC 8288, RFC 9530]
- **AGSC-06-11** `digest` values are defined once, in AGSC-06-08; `agsc-ledger-head` MUST be the lowercase hex `hash` of the last entry of the derived ledger of §08 — the head that `verify --ledger` recomputes and compares. A ledger always has at least the trailing `build` entry (AGSC-08-20a), so the head is never undefined where the attribute is required; a Level-0 node publishes no `rel#ledger` link and therefore no head (AGSC-06-08a). `agsc-generated-at` MUST derive from `SOURCE_DATE_EPOCH`. [PRD-005, PRD-024]
- **AGSC-06-12** VoID (`/.well-known/void`, registered 2011) is prior art for dataset discovery and is cited as complementary wherever this specification describes its discovery layer (an editorial commitment, not a conformance requirement). This specification **emits no VoID description**: `graph.jsonld` on the `describedby` link already carries the bundle-level facts (AGSC-06-08), AGSC-06-01's route set is closed, and a SHOULD-emit with no route would be unimplementable. A node that publishes a VoID description independently SHOULD link it from the link set as a second `describedby` link (AGSC-06-09 admits several; AGSC-06-08's "nowhere else" binds the `agsc-*` bundle-facts attributes to the `graph.jsonld` link, not the number of `describedby` targets). [design]
- **AGSC-06-35** **Related-system links, OPTIONAL and extensible.** The discovery document MAY carry, in its one link context, links to related discovery documents and systems — an llms.txt v2 file, a VoID or DCAT description, an OKF index, an Agent2Agent Agent Card, an MCP server card, an Agentic Resource Discovery manifest, a publisher-curated LLM context file, an agent-memory, ontology, knowledge-graph or SPARQL endpoint, a runtime or architecture registry — so that any agentic-AI, knowledge, memory or ontology system that this node relates to can be reached from it, and so that new ones can be added without a change to this specification. Such links use **IANA-registered relations only**, chosen by meaning: `describedby` (the target describes this node), `alternate` (the same knowledge in another representation), `related` (a related resource), `service-desc`, `service-doc` and `service-meta` (an interface this node exposes or points at), `collection` and `item` (containment), and `cite-as` (RFC 8574: the target is preferred over this node for the purpose of permanent citation — a concept DOI's landing page, for instance, configured with `type: "text/html"`) *(`cite-as` is IANA-registered, so this list's registered-names-only condition admits it, and it lets a node that has deposited a release say which identifier to cite)*. Each MUST carry `type` and MAY carry `profile` (RFC 6906) and `title`. They are configured in `agsc.config.json` as `related[]{rel, href, type, profile?, title?}` (AGSC-01-18; `rel` from the list above, `href` absolute `https:`), emitted in `href` order within each relation (AGSC-06-10), and never derived from content. A reader MUST ignore a related-system link it does not understand; no related-system link affects conformance, any digest, the peer check or the walk (AGSC-11-10 follows `rel#peer` only), and none is ever required at any Level. An unregistered short name (`ard`, `llm-context`, …) MUST NOT be used until IANA registers it — a MINOR adds it then — and a relation not in the list above is `AGSC-E209`. [design]

## 6.3 llms.txt

## 6.4 Machine surfaces and headers

- **AGSC-06-16** `search.json` MUST be a prebuilt inverted index `{terms:{token:[docIndex…]}, docs:[{slug,title,description,cluster}]}` requiring no runtime dependency. `docs[]` MUST be ordered by slug, each posting list MUST be ascending `docIndex` values without repetition, and the `terms` member names MUST be ordered as JSON member names per AGSC-04-05. Tokens are produced by AGSC-06-23 and by nothing else. An item with no `clusters[]` omits the `cluster` member, and an item with no `description` omits `description`; a member is never emitted as the empty string, so `search.json` stays a function of the authored keys — unless AGSC-06-21 applies, in which case this document is the manifest that rule defines. [PRD-014]
- **AGSC-06-23** **Tokenizer (normative).** For each item the tokenizer input is, in this order, `title`, `description`, every `tags` value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are **not** token characters. A token character is `[a-z0-9]` or a character whose Unicode General_Category is `L*` (any letter), `Nd` (decimal digit) or `M*` (combining mark, so Devanagari and Thai words are not split); every other character — including `No`/`Nl` forms such as `²` and `Ⅷ`, and `Lo`-adjacent symbols — is a boundary. Non-ASCII letters and digits are kept code-point-wise and never transliterated. The General_Category table is that of the Unicode version pinned by AGSC-04-22. That pin is **16.0.0**; a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). There is no stemming, no stop-word list, no synonym expansion and no n-gram: two conforming engines therefore emit byte-identical `search.json`. [PRD-014, NFR-04]
- **AGSC-06-17** `_headers` MUST set `Content-Type: text/markdown; charset=utf-8; variant=GFM` for `/pages/*.md`, `Content-Type: application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"` for `/.well-known/knowledge-linkset` — or the header fallback of AGSC-06-07 — and a `Content-Security-Policy` that contains at least `default-src 'none'`, `script-src 'self'`, `style-src 'self'`, `img-src 'self'` and `connect-src 'self'` — the least the required pages need: the stylesheet every page links, the images it shows, and the search index and the page tools' reads, all from the node itself — and admits no inline script; a writer MAY add directives that only restrict further (`base-uri 'none'`, `form-action 'none'`, `frame-ancestors 'none'` in the reference engine), and a case on the policy asserts that it contains these directives, never the whole string. *(Amended 2026-10-02 for 1.0.0: until `1.0.0-rc.6` the rule named `default-src 'none'` with `script-src 'self'` alone, a policy under which the pages the same chapter requires could not load their stylesheet or their search index.)* `_redirects` MUST carry `/.well-known/agentic-knowledge` → 301 → `/.well-known/knowledge-linkset`, and this alias MUST be present until the last 0.0.x consumer is retired. A writer MAY additionally emit, for each machine artefact of AGSC-06-01, a served `Repr-Digest: sha-256=:<base64>:` header whose value is the base64 of the same SHA-256 the discovery document carries as that link's `digest` (AGSC-06-08). The field is RFC 9530's, a Structured Fields Dictionary whose value is a Byte Sequence (RFC 9651) and whose algorithm token is `sha-256`; a writer that emits it MUST derive it from the emitted bytes and never from a separate computation. It is a MAY and no Level requires it, so the required header set of this rule and the bytes `build-0012` pins are unchanged. *(Rationale: a reader holding one fetched file can check it without a second fetch of the discovery document.)* [PRD-020, RFC 7763, RFC 9530]
- **AGSC-06-18** One licence policy is expressed in exactly **three** machine-readable dialects at 1.x, and no more: the AI-usage signals of `robots.txt` (RFC 9309); the TDMRep policy at `/.well-known/tdmrep.json` (the TDM Reservation Protocol well-known location, and the **only** route that carries it — the duplicate copy at `/tdmrep.json` is not emitted); and the `schema:license`/`schema:usageInfo` members of the JSON-LD views together with `llms.txt`. `rsl.xml` and the aipref `Content-Usage` field are **not** emitted at 1.x, and no rule, route or claim may assert them. The three dialects express one policy at three levels of precision, and only what is **comparable** is compared: a TDMRep `tdm-reservation` of `1` MUST be accompanied by a `robots.txt` group `User-agent: <token>` with `Disallow: /` for every product token (RFC 9309 §2.2.1) of `site.tdm_crawlers[]` (AGSC-01-18), and by a `schema:usageInfo` naming the Content Use Terms; a disagreement on those three comparable facts MUST fail the build, and nothing else is compared. `site.tdm_crawlers[]` is the **publisher's own, maintained** list of the product tokens whose operators state that they collect content in order to train a machine-learning model; it is configuration and never a constant of this specification, because vendors rename tokens and add them and a list frozen into a standard goes stale where it matters most. A writer MUST emit one such group per token, in the order the configuration states them and before the `User-agent: *` group, and MUST NOT emit a `Disallow` for any token the list does not name — a fetch made on a person's behalf, and a search crawler, stay invited, which is what keeps a node readable by the agents it exists for. An empty `site.tdm_crawlers[]` on a node that publishes `tdm-reservation: 1` is `AGSC-E202` at build, because the Content Use Terms text this rule pins by hash tells the reader that the reservation is stated machine-readably by the TDM reservation file **and the robots signals of this node**: with no token named, those signals carry no reservation and the node's own prose is false. *(Rationale: with no token named, the `Disallow` conjunct would be vacuously true, and the one machine-checkable link between the strongest dialect and the weakest could never fail.)* `robots.txt` expresses crawler access, not licence: RFC 9309 defines only User-Agent, Allow and Disallow and says of them "These rules are not a form of access authorization" (read 2026-09-19). *(Rationale: no rule defines a mapping between the three dialects, and RFC 9309 has no vocabulary in which a TDM reservation or a `schema:license` can be expressed at all, so only the comparable facts are compared.)* The **Content Use Terms identifier** is the constant `LicenseRef-AgenticSystemCore-Content-Use-1.0`. The Content Use Terms accompany the prose only where the publisher adopts them — `bundle.license_prose` is that identifier, or is absent and defaults to it (AGSC-01-18) — and every prose-carrying export of such a node MUST embed the identifier; a build omitting it MUST fail. A Bundle whose prose carries another licence MUST NOT be presented under terms narrower than that licence: wherever this specification places the Content Use Terms identifier — the `terms:` line of AGSC-06-13a, the `terms` member of a chunk line (AGSC-06-26), a skill pack or a Harness (AGSC-07-16), `schema:usageInfo` (AGSC-05-26) — such a node places the value of `bundle.license_prose`; it publishes `tdm-reservation: 0` and no crawler group, and its pages name its own licence and not the Content Use Terms. `license` and `terms` are two members with two meanings even when their strings coincide. *(Rationale: the Content Use Terms reserve model training, and a licence that grants more may forbid adding restrictions to it.)* The Content Use Terms **text** is shipped as `LICENSE-CONTENT` at the Bundle root (AGSC-01-26); a distribution without it is incomplete. **The text the identifier names is the file `LICENSE-CONTENT` at the root of this specification's distribution, whose SHA-256 over its bytes is `b2e8da62e6a41886296d2d2358fb4642cc7418e806eb4a29ada12b588ac32857` (2133 bytes).** A distribution that ships different text MUST use a different identifier: the identifier names terms, not a file name, and reusing it over other wording would make every `terms:` line of AGSC-06-13a and every `schema:usageInfo` of AGSC-05-26 unverifiable. A reader MAY check the hash; nothing requires a node to publish it, because the terms are the same terms for every node that carries the identifier. A writer MUST emit `/legal/` from that `LICENSE-CONTENT` file when the Bundle root carries one, and MUST NOT emit the Content Use Terms link on any page when it does not; `/about/` and `/changelog/` remain authored and optional (AGSC-06-01). The `/legal/` page MUST also carry, each only where the Bundle supplies its input: the publisher's **privacy notice and retention statement**, from an authored `PRIVACY.md` in the Bundle root, rendered unchanged; an **identification of the operator**, derived from `site.author` and `bundle.operator` (AGSC-01-18, AGSC-01-25); and the **AI-assistance statement** of AGSC-06-15, in the same words the provenance header of every agent-facing export carries. A writer MUST NOT invent any of them — a privacy notice that is not the publisher's own words is worse than none — and an absent input omits that section and is the warning `AGSC-E406`, naming what is missing. *(Rationale: PRD-019 asks this page for the Content Use Terms, a privacy notice, the operator and a retention statement.)* [PRD-019]
- **AGSC-06-19** `sitemap.xml` MUST list every published route with `lastmod` from the build instant, ordered by URL. A **published route** is every route of AGSC-06-01 that the build emits as an HTML page — the home page, every item page, every index page (`/<type-plural>/`, `/clusters/`, `/clusters/<slug>/`, `/tags/<tag>/`, `/<route>/page-<n>/`), `/now/`, `/compose/`, `/search/`, `/skills/` and, where the build emits them, `/about/`, `/legal/`, `/changelog/`, `/conformance/`, `/boards/<cluster-slug>/` and `/specs/**` — and never `/404.html` or a machine file. Schema.org JSON-LD (`TechArticle`, `DefinedTerm`, `Dataset`) MUST be embedded in item and index pages. [PRD-020]
- **AGSC-06-20** Generated HTML MUST meet WCAG 2.2 AA — semantics, keyboard operability, contrast, and `alt` text from the diagram's `alt` key. [NFR-08]
- **AGSC-06-21** Budgets are normative and MUST fail the build when exceeded: ≤100 KB per HTML page; ≤1 MB per **index document** — `/search.json` at or below 500 items, and each `/search-<nn>.json` shard above it, every shard carrying the docs of at most 500 items (AGSC-06-31 already describes this rule's sharding that way); ≤60 s build **per 500 items** (external page requests are already impossible under AGSC-06-05). `KB` and `MB` are the decimal prefixes — 1,000 and 1,000,000 UTF-8 bytes of the emitted document — and AGSC-01-16 writes `MiB` where it means the binary prefix. *(Rationale: AGSC-06-23 puts each item's body into the index, so the index costs what the prose costs, and per-item bytes fall as a Bundle grows, because the vocabulary amortises, and rise with body length; the budget is therefore stated once, on the artefact a reader actually downloads. At a full 500-item shard this bound is 2 KB of index per published item; how much one item can contribute to a page is already bounded by the 100 KB page budget of this rule.)* Above 500 items a writer MUST shard the index as `/search-<nn>.json` (`<nn>` zero-padded from `01`, in slug order) with `/search.json` as the manifest `{shards:[…], docs_total}` (and `/chunks.jsonl` sharded on the same trigger and in the same shape, AGSC-06-31), and MUST paginate any index route carrying more than 500 entries as `/<route>/page-<n>/` (`<n>` from `2`; page 1 is the route itself). The **index routes** are exactly these and no others: `/`; each `/<type-plural>/` — `/concepts/`, `/procedures/`, `/lessons/`, `/episodes/`, `/gates/`, `/clusters/`; each `/tags/<tag>/`; and `/search/`. An item page, `/now/`, `/compose/`, `/about/`, `/legal/`, `/changelog/`, `/specs/**`, `/ns/**` and `/skills/**` are not index routes and are never paginated. Each `/search-<nn>.json` shard is a complete AGSC-06-16 index over the items of its own slice: its `docs[]` is the contiguous run of the slug order that the shard carries, and its posting values are indices into **its own** `docs[]`, counted from zero. A reader reconstructs the whole index by concatenating the shards' `docs[]` in manifest order and adding, to every posting of a shard, the number of documents the earlier shards carry. A reader that cannot obtain every shard the manifest names MUST report `AGSC-E901` rather than answer over the part it holds. *(Rationale: the other reading of a shard's `docIndex` answers wrongly and silently on every shard but the first.)* The budgets are therefore per-scale, not absolute, and a 5,000-item Bundle conforms: it publishes ten index shards, each under the bound. Exceeding a budget that no sharding rule relieves MUST fail the build, with `AGSC-E904` *(the code of the size caps of AGSC-01-16 and AGSC-01-34)*. [NFR-06]
- **AGSC-06-22** `/now/` and `/now.md` MUST be generated from stored state only — counts, last build, stale items, open Lessons, monthly spend — never hand-edited. A section whose input is absent MUST be omitted, not guessed. Both MUST carry, as one line and its own paragraph, `content version <bundle_version>, built at <instant>, fingerprint <bundle-hash>, specification <spec_version>` — the four values of AGSC-04-25, AGSC-04-09, AGSC-04-15 and AGSC-00-17, in that order and with those separators — so that a reader who opens one file learns which content, built when, hashing to what, against which version of this specification; the rest of the page's layout is implementation-defined and no rule pins a byte of it. [PRD-015]

- **AGSC-06-24** `/about/` MUST include a "Quickstart" section with one ≤10-line path per persona P0–P11 (P0 first: the three commands), generated from a template so it cannot drift from the verb set. `/about/` and the Internet-Draft's Security Considerations MUST both carry the AGSC-08-19 honest-limit statement verbatim. When a Bundle authors `/about/` itself (AGSC-06-01), the writer MUST still insert the generated Quickstart section and the AGSC-08-19 statement into that page; a node that emits no `/about/` — the route is conditional — has no obligation under this rule. [PRD-052]
- **AGSC-06-25** A writer (Level 2 and above) MUST emit, in the `<head>` of every generated HTML page, `<link rel="describedby" href="/.well-known/knowledge-linkset" type="application/linkset+json">`, and SHOULD send the equivalent `Link: </.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json"` response header on `/` and MAY send it on any other page (AGSC-11-05). A Level-0 publisher SHOULD do the same, so that a CMS or wiki export that cannot inject a `<head>` element still claims Level 0 (AGSC-10-02). `describedby` is the IANA-registered relation — registered by the W3C POWDER Recommendation (POWDER-DR Appendix D, used in §4.1.4, 2009); RFC 6892 registers its inverse `describes` — whose meaning — "the target describes the context" — is exactly this link's; what *kind* of description is said by the target's media type and by the profile URI (AGSC-06-07), never by a new relation name. A page may carry several `describedby` links (llms.txt v2 uses the same relation for its context file): a reader selects this one by `type="application/linkset+json"`, and a reader that fetches it confirms the profile. **No link relation is requested from IANA**: the Internet-Draft requests registration of the well-known suffix only, and registration of the Profile URI is requested separately under RFC 7284 (AGSC-06-07), so no extension-URI spelling and no later alias ever exist. [PRD-024, RFC 6892, RFC 9264]
- **AGSC-06-34** **Agent card, OPTIONAL emission.** A node MAY emit `/.well-known/agent-card.json` only when it declares both the `a2a-card` and a `responder` surface (AGSC-11-16, AGSC-11-21): the card is the Agent2Agent 1.0 Agent Card whose interfaces point at that responder, with `protocolVersion` equal to the `agsc-surface-version` declared for `a2a-card`, serialised JCS-canonical (AGSC-04-05) plus one trailing LF, and it MAY carry `signatures[]` per A2A §8.4 (JWS over the JCS form). A node with no responder MUST NOT emit the card (AGSC-06-07). [A2A 1.0 §8]

## 6.5 Agent-retrieval chunk export

- **AGSC-06-26** A Level ≥ 2 writer MUST emit `/chunks.jsonl`: one JCS-canonical JSON object per LF-terminated line, one line per **chunk**, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the `chunks` surface (AGSC-11-16). This shape holds unless AGSC-06-31 applies, in which case this document is the manifest that rule defines. [PRD-061]
- **AGSC-06-27** **Boundary rule.** Chunks are cut **after** the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every **ATX** heading of level 2 or 3 (`## `, `### `) that lies **outside any fenced code block**, per CommonMark 0.31.2 (AGSC-02-20) — a `## ` line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's `text` ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds `chunks.max_bytes` (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's `text` end without LF and the next begin mid-line. No overlap. The heading is not repeated into continuation chunks. [design]
- **AGSC-06-28** **Identifier.** `id` is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by `#chunk-` and the first 16 hex characters of `id`, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [design]
- **AGSC-06-29** **Record shape.** Members, all REQUIRED unless marked: `digest` (lowercase-hex SHA-256 of the UTF-8 bytes of `text`), `id`, `iri` (the item IRI), `item` (the slug), `kind` (the item type), `subkind` (OPTIONAL: the concept `kind`, present only on concepts), `license` (`bundle.license_prose`), `links` (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order) in JCS order; a target naming an item excluded by AGSC-06-30 is dropped from its array and a key emptied by that drop is omitted (the exclusion every other surface applies); OPTIONAL when empty), `ordinal`, `section` (the anchor; empty for chunk 0), `terms` (the Content Use Terms identifier of AGSC-06-18), `text`, `title`, `trust` (always `untrusted` — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), `type` (`text`, or the media type of an attachment chunk, AGSC-06-30). A 1.0 writer emits no other member; `x-<vendor>-<key>` members MAY follow (AGSC-02-05a), a later MINOR may add members, and a reader MUST ignore a member it does not know (AGSC-00-21). Lines are ordered by item slug (code point), then `section` (code point), then `ordinal` ascending numerically. [PRD-061, AGSC-11-18]
- **AGSC-06-30** **Exclusions and attachments.** Items with `status` `retired` (AGSC-11-22) or `draft`, and items held back by the `releases` switchboard (AGSC-01-20), are excluded — the same set that `search.json` and `/llms.txt` exclude; a cluster contributes one chunk (its description; a cluster without `description` contributes no chunk). Each attachment of an item (AGSC-02-98) contributes one chunk whose `type` is the attachment's media type, whose `text` is the attachment's `alt` text for binary media and the file's full text for `image/svg+xml` and other text media, whose `section` is `attachment-<n>` (`<n>` the 1-based index in `attachments[]`) and whose `ordinal` is `0`; a cluster's chunk has `item` = the cluster slug, `iri` = the cluster IRI, `section` empty and `ordinal` `0`. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [design]
- **AGSC-06-31** Budgets: `/chunks.jsonl` MUST NOT exceed 8 KB per published item on average; above 500 items a writer MUST shard as `/chunks-<nn>.jsonl` (`<nn>` zero-padded from `01`, each shard the lines of at most 500 items in slug order, no item split across shards) with `/chunks.jsonl` becoming the JCS-canonical manifest `{"bundle_version": <string>, "lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]}` (paths in shard order; `bundle_version` is the content version of AGSC-04-25, and a chunk line does not carry it, its member set being closed by AGSC-06-29), exactly as AGSC-06-21 shards the index. A chunk line carries no index into any other line, so AGSC-06-21's shard-reading rule has no counterpart here: a reader concatenates the shards in manifest order and needs nothing else (so that a reader of the two sharding rules does not look for a rule that is deliberately absent). [AGSC-06-21]

## 6.6 JSON-LD context file

- **AGSC-06-32** A Level ≥ 2 writer MUST emit `/ns/context.jsonld`, the target of the `…/rel#context` link (AGSC-06-10) and of the `application/ld+json` branch of `/ns/` negotiation (AGSC-06-06). It MUST be generated from `ontology/agsc.ttl` by a deterministic mapping — every `asc:` term becomes a term definition whose `@id` is its IRI, object properties carry `@type` `@id`, datatype properties carry the `@type` of their declared range, and — because `graph.jsonld` also uses external vocabularies — the prefixes `dcterms`, `prov`, `rdfs`, `schema`, `skos` and `xsd` are defined together with a typed term definition for every external property a rule of §05, §06 or §11 emits (`rdfs:seeAlso` as `@id`, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to `null` (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used); `@version` 1.1 and `@protected` true are set — sorted per AGSC-04-05, and MUST round-trip: expanding `graph.jsonld` with it and re-compacting MUST reproduce `graph.jsonld` **as a value**, and MUST reproduce it byte for byte once the compacted result is serialised in the canonical form of AGSC-04-05 (JCS over NFC strings), which is the form `graph.jsonld` is written in — a JSON-LD processor fixes no member order, so the canonical serialisation is the step that makes the comparison a byte comparison. The term **name** of an `asc:` term is its local name; the term name of an external property is its local name, or its compact IRI (`<prefix>:<local>`) where that local name is also an `asc:` term name or is shared by two external properties. The full context file is therefore a constant of this specification, derived from `ontology/agsc.ttl` and from nothing about a node, and a node's `/ns/context.jsonld` MUST equal it byte for byte (AGSC-05-09). *(Rationale: the member names of `graph.jsonld` are these term names, and AGSC-04-24 claims byte-identity for `graph.jsonld` across implementations; the vector `graph-0011` uses the bare local name.)* Released context files are immutable (AGSC-00-16); the versioned copy lives at `/ns/<version>/context.jsonld`. [AGSC-05-09]

## 6.7 Static query fragments (SHOULD, sacrificial)

- **AGSC-06-33** A Level ≥ 2 writer SHOULD emit `/graph/fragments/s/<subject-hash>.nq` for every distinct subject IRI and `/graph/fragments/p/<predicate-hash>.nq` for every distinct predicate IRI of `graph.nq` — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus `/graph/fragments/index.json` `{subjects, predicates, generated_at}` — JCS-canonical, `subjects` and `predicates` arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. *(Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.)* [design]

## 6.8 Dataset vocabularies — VoID and DCAT (informative)

VoID is cited as complementary prior art by AGSC-06-12 (a MUST). DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator MAY use to describe a Bundle **as a dataset**; this specification defines no DCAT emission and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to `ontology/agsc.ttl`. Where a publisher emits it, the natural mapping is: the Bundle IRI is a `dcat:Dataset` (and, being a `skos:ConceptScheme`, also the `dcat:themeTaxonomy` of its own catalogue record); `dcterms:title`/`dcterms:description` from `site.title`/`content/index.md`; `dcterms:license` from `bundle.license_prose`; `dcterms:modified` from the build instant; each machine artefact of AGSC-06-01 is a `dcat:Distribution` with `dcat:accessURL` the route, `dcat:mediaType` the served type and `spdx:checksum` the same SHA-256 the link set carries as `digest`; the discovery document itself is the `dcat:landingPage`-adjacent entry point, and the `…/rel#graph` targets are the distributions a triple-store consumer wants. A VoID description (`void:Dataset`, `void:dataDump` = `/graph.nq`, `void:vocabulary` = the `/ns/` IRI) may sit beside it at `/.well-known/void`; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.
