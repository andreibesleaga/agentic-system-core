# AGSC-06 — Published surfaces: routes, discovery files, llms.txt

## 6.1 Route set

- **AGSC-06-01** A writer MUST emit exactly this route set into `build.out` (default `www/`): `/`; `/concepts/` and `/concepts/<slug>/`, plus `/<type-plural>/<slug>/<lang>/` for every language variant (AGSC-01-13); `/procedures/`, `/lessons/`, `/episodes/`, `/gates/` with their item pages; `/clusters/` and `/clusters/<slug>/`; `/tags/<tag>/`; `/search/` with `/search.json`, plus `/search-<nn>.json` shards and `/<route>/page-<n>/` index pages above the bounds of AGSC-06-21; `/now/` and `/now.md`; `/compose/`; `/skills/`, `/skills/index.json`, `/skills/<cluster>/SKILL.md`; `/specs/` and `/specs/agentic-knowledge/`, plus `/specs/mcp/` when the `mcp` surface is declared (AGSC-11-16) (the published specification of the AGSC-06-07 profile URI, the 303 target of the w3id `profile/agentic-knowledge` rule, which MUST carry an anchor `#link-relations` and one anchor **named exactly as the fragment of the relation URI** — `#graph`, `#ontology`, `#context`, `#now`, `#skills`, `#ledger`, `#peer`, `#surface`, `#contribute`, `#access` — per AGSC-06-10 extension relation, so that a client that does follow an extension relation URI lands on that relation's documentation; RFC 8288 §2.1.2 permits that but discourages it, saying "clients SHOULD NOT automatically access that resource to avoid overburdening its server" *(amended at rc.5, V9A-05: the anchors were named `#rel-<name>` while the w3id `^rel/?$` redirect carries no fragment of its own, so a client following `…/rel#graph` kept `#graph` and landed on a fragment that does not exist — all ten of them; and §2.1.2 was cited as if it required dereferenceability)*); `/ns/context.jsonld` and `/ns/<ontology-version>/context.jsonld` (AGSC-06-32, AGSC-05-09), which are the only `/ns/` routes a content node emits — the vocabulary documents `/ns/agsc.ttl`, `/ns/agsc.rdf` and the `/ns/` HTML index are published by the namespace document site alone, which is what the w3id negotiation of AGSC-06-06 resolves to *(amended at rc.6, NS-05 and ENG4-05: this enumeration read "`/ns/` and its vocabulary files", an unbounded obligation that no content node can discharge — `w3id/.htaccess` redirects every `/ns/…` request to the namespace site — while AGSC-05-09 as amended at rc.5 requires a Level ≥ 2 writer to serve the versioned copy that this enumeration did not carry, so the two rules could not both be satisfied)*; `/about/`; `/legal/`; `/changelog/`; `/graph.jsonld`, `/graph.ttl` and `/graph.nq`; `/pages/<slug>.md` and `/pages/<slug>.jsonld`; `/attachments/<slug>/<file>` for every attachment an item names (AGSC-02-98; the served bytes are the hashed bytes of AGSC-05-29 — AR2-23); `/assets/<path>` for every file under `content/assets/` that a published item's body references (AGSC-03-11), `<path>` being that file's path relative to `content/assets/` and the served bytes being the authored file's bytes *(added at rc.6, FIX28-01: AGSC-03-11 admits a body image or link into `content/assets/` and AGSC-02-95 creates such files during adoption, byte for byte, while this route set carried no route for one — so the two rules were jointly unsatisfiable and every Bundle that used the branch published a reference that 404s)*; `/llms.txt` and `/llms-full.txt`; `/sitemap.xml`; `/robots.txt`; `/.well-known/tdmrep.json`; `/ledger.jsonl`; `/chunks.jsonl` and its `/chunks-<nn>.jsonl` shards (AGSC-06-26/31); `/boards/index.json` and `/boards/<cluster-slug>.json` when the Bundle holds at least one task item (AGSC-10-13); optionally `/graph/fragments/**` with `/graph/fragments/index.json` (AGSC-06-33); `/.well-known/knowledge-linkset`; `/.well-known/security.txt`; `/404.html`; and, for the **Cloudflare Pages deployment profile**, `_headers` and `_redirects` (AGSC-06-17).

  A writer targeting another host MUST emit the equivalent configuration for that host and MUST state which deployment profile it emitted in its conformance claim (AGSC-09-01); the normative content is the header set of AGSC-06-17, AGSC-11-03 and AGSC-11-05 and the redirect of AGSC-06-17, never the file format. This route set bounds what a writer MUST emit; it is not a bound on every file that may sit in the deployed directory, and the same-origin script assets a page of this set loads — `/compose/` and every item page load them so that the page tools of AGSC-09-16 can be registered, and AGSC-06-17's `script-src 'self'` policy leaves a writer no inline alternative — are emitted as part of the page that names them and are not routes of their own *(added at rc.6, ENG3-S5 and R1-03: the scripts are now four and are loaded from every item page as well as from `/compose/`, so reading them as assets of one route had stopped being true, and nothing said whether "exactly this route set" bound the writer's emission or the deployed directory)*. *(Amended at rc.5, V9A-08: `_headers` and `_redirects` are Cloudflare Pages configuration files whose grammar no rule pins, and holding a Level-2 writer on nginx, Apache, S3 + CloudFront or a Solid pod to them made every Level-2 claim implicitly Cloudflare-shaped.)*

  `/ledger.jsonl` is the derived ledger of §08, published so that a reader can recompute the chain offline (AGSC-08-23) and so that the `rel#ledger` link of AGSC-06-10 has a target. `/search/` and `/search.json` are unconditional (AGSC-06-16 MUSTs the index). The conditional routes are the shards and index pages of AGSC-06-21/06-31 (by size), `/boards/**` (by the presence of a task), `/specs/mcp/` (only when the `mcp` surface is declared, AGSC-11-16), `/.well-known/agent-card.json` (only under AGSC-06-34), `/legal/` (only when the Bundle root carries a `LICENSE-CONTENT` file, AGSC-06-18 as amended at rc.5, V9D-05), `/conformance/` (only when a claimant publishes the report AGSC-09-03 defines, which is a MAY), `/.well-known/void` (only when a publisher emits a VoID description independently, AGSC-06-12, which is a SHOULD-link and never an emission of this specification), `/.well-known/security.txt` (only when the Bundle root carries an authored `.well-known/security.txt` that states a `Contact:` field — AGSC-06-36, added at rc.6, PSF-02), `/assets/<path>` (one route per authored asset file a published body references) and the optional `/graph/fragments/**` (AGSC-06-33); no other route is conditional. *(The first two of those were added to this list at rc.5, V8-96: AGSC-09-03 and AGSC-06-12 contemplated both routes while this rule said "exactly this route set" and "no other route is conditional".)* `/graph.rdf` and `/feed.xml` are **not emitted at 1.x**, and `build.rdfxml` and `build.feed` are reserved names rejected with `AGSC-E004` (D82 Q21; `feed` reserved at rc.5, R-15 — no 1.0 rule pins a feed's bytes, so the route could not be derived, the switch had nothing to switch on, and a writer could not discharge the MUST).

  `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CITATION.cff`, `CONTRIBUTING.md`, `GOVERNANCE.md`, `CONTRIBUTOR-AGREEMENT` (AGSC-08-06, added to this list at rc.6) and the REUSE layout are repository files, not routes (PRD-047); only `security.txt` is published, at its RFC 9116 location above, and what it carries is AGSC-06-36's (added at rc.6, PSF-02). [PRD-011 ← R36, audit/D §5, V2-05/06/07]
- **AGSC-06-02** Item pages MUST link their own `/pages/<slug>.md` and `.jsonld`. An empty type folder MUST be omitted from navigation but MUST still resolve. [audit/D §5]
- **AGSC-06-03** The site identity is software plus registry. A reading order, a "start here" sequence, chapter structure or companion framing MUST NOT be emitted. [R23, Art. XIII]
- **AGSC-06-04** `/404.html` and the host configuration of the writer's deployment profile — `_headers` and `_redirects` for Cloudflare Pages (AGSC-06-01 as amended at rc.5, V9A-08) — MUST be generated, never hand-maintained; a renamed or superseded slug MUST produce a redirect entry in that configuration. [PRD-018, PRD-020]
- **AGSC-06-05** Pages MUST NOT reference a third-party origin, load a font, script or image from another host, set a cookie, use `localStorage`, or emit a beacon. [PRD-046 ← R52, N4]
- **AGSC-06-06** `/ns/` conneg is done by the w3id `.htaccess`, mapping `Accept` to a fixed table of same-origin static targets (`text/turtle` → `/ns/agsc.ttl`, `application/ld+json` → `/ns/context.jsonld`, `application/rdf+xml` → `/ns/agsc.rdf`, else the HTML index) — plus the legacy `Accept` aliases `application/x-turtle` (→ Turtle) and `application/json` (→ JSON-LD), which a node MAY accept and no node need send — plus one path rule that sends `/ns/<major>.<minor>.<patch>(/…)?` to the immutable versioned copy of that release before any term rule can capture it (`owl:versionIRI` must resolve). No project-owned server code exists; `/ns/<version>/…` copies are immutable. [D41, D47, ADR-005]

## 6.2 The well-known file

- **AGSC-06-07** There MUST be exactly one discovery file, `/.well-known/knowledge-linkset`, served as `application/linkset+json` carrying the RFC 9264 §5 profile parameter `profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"`. Where the hosting platform cannot carry a parameter on `Content-Type`, the node MUST instead send the response header `Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile"` (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served (D55 amends D21-final/D41/D47-note(c)). Separate manifests MUST NOT be emitted; a release MAY carry a copy named `knowledge-linkset.json`. `agent-card.json` MUST NOT be published unless the node declares it as the `a2a-card` surface **and** declares a `responder` surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is `AGSC-E210`. The well-known suffix `knowledge-linkset` (D60 supersedes D56's ordering) is **pending registration** under RFC 8615 through the Internet-Draft, and the Profile URI is filed under RFC 7284 (First Come First Served); the discovery link uses the already-registered relation `describedby` (AGSC-06-25, D82 Q3), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with `describedby` and the linkset media type — nothing in this specification says "registered" of the suffix or the profile before the registry does. **The suffix is a single point of substitution** (D82 Q4): the reference implementation holds it as one constant (`WELLKNOWN_SUFFIX`) from which the `peers[]` schema pattern, the `_redirects` alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next rung of the D60 ladder by one PATCH and a regeneration. [PRD-024 ← D55, D56, D60, RFC 9264, RFC 9727 §7.3, RFC 6906]
- **AGSC-06-08** The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose **sole** top-level member is `linkset` (RFC 9264 §4.2.1); no other top-level member may be present; the `linkset` array holds exactly one link context object whose `anchor` is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05) — AR2-38. Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link MUST carry `digest`, a Dictionary with a single member whose key is the RFC 9530 algorithm name `sha-256` and whose value is an RFC 9651 §3.3.5 **Byte Sequence**, serialised per RFC 9651 §4.1 as `sha-256=:<base64>:` and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's `describedby` link to `graph.jsonld` and nowhere else: `agsc-spec-version` (one value), `agsc-generated-at` (one value, an AGSC-04-10 instant derived from `SOURCE_DATE_EPOCH`), `agsc-counts` (one `"<type-plural>=<n>"` string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30 (AR2-39)), `agsc-bundle-hash` (the AGSC-04 bundle hash, RFC 9530 syntax), and `agsc-bundle-version` (one value, the content version of AGSC-04-25 — added at rc.6, D113: the hash says whether two nodes hold the same content and never what the publisher calls that content, so a reader that wants to cite or compare releases needs both). The ledger is the link `https://w3id.org/agentic-system-core/rel#ledger`, carrying `digest` and `agsc-ledger-head` (one value, the lowercase hex head of the derived ledger of §08). A node MAY carry one further link whose relation is `https://w3id.org/agentic-system-core/rel#signature` (AGSC-06-10) and whose target is a detached signature over the canonical bytes of this document. At 1.x no rule pins the signature format, no Level requires the link, it affects no digest, no claim and no walk, and a reader MUST ignore it if present. *(added at rc.6, 2026-09-23, EXT2-07. Non-normative: the digests of this rule establish that the bytes are the bytes the publisher hashed; they establish nothing about who the publisher is. The trust anchor at 1.x is the origin's TLS certificate and DNS name, and a publisher who needs more publishes the optional signature. The nearest comparator, the Agent2Agent Agent Card, makes a signature over its canonical card optional ("Agent Cards MAY be digitally signed", A2A §8.4, read 2026-09-16 and quoted in `docs/SECURITY-CONSIDERATIONS.md` §2); this specification keeps its own optional for the same reason and one more — a static node has no key custody — and the reasoning is written here rather than left to inference. No IANA-registered relation exists for a signature — the registry was read on 2026-09-23 and holds none — so the link can only take this specification's own extension-URI form, and AGSC-06-35's registered-names-only list cannot admit it.)* [PRD-024 ← D55, RFC 9264, RFC 9530, RFC 9651 ← V5-3 S3-04, S3-08]

Example — the document served at `/.well-known/knowledge-linkset`:

```json
{
  "linkset": [
    {
      "alternate": [ { "digest": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "href": "https://example.org/llms.txt", "type": "text/plain" } ],
      "anchor": "https://example.org/",
      "describedby": [ { "agsc-bundle-hash": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "agsc-bundle-version": ["v1.0.0"], "agsc-counts": ["clusters=0","concepts=0","episodes=0","gates=0","lessons=0","procedures=0"], "agsc-generated-at": ["2026-01-01T00:00:00Z"], "agsc-spec-version": ["1.0.0-rc.6"], "digest": ["sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:"], "href": "https://example.org/graph.jsonld", "type": "application/ld+json" } ],
      "https://w3id.org/agentic-system-core/rel#graph": [ { "digest": ["sha-256=:…:"], "href": "https://example.org/graph.ttl", "type": "text/turtle" } ],
      "https://w3id.org/agentic-system-core/rel#ledger": [ { "agsc-ledger-head": ["bee9ba6593162f59dae28f42ba25fa04ea3fd65ae4f80685fb1c4ede151189ac"], "digest": ["sha-256=:…:"], "href": "https://example.org/ledger.jsonl", "type": "application/jsonl" } ],
      "license": [ { "href": "https://example.org/legal/" } ],

```

The example is shown pretty-printed for review; the served bytes are JCS-canonical with exactly one trailing LF (AGSC-04-04).

- **AGSC-06-08a** At **Level 0** (AGSC-10-02) the document is the **same** link set with every `digest` and every `agsc-*` attribute of AGSC-06-08 (`agsc-spec-version`, `agsc-generated-at`, `agsc-counts`, `agsc-bundle-hash`, `agsc-bundle-version` — the last added at rc.6, D113 — and `agsc-ledger-head`) omitted — the §11 attributes (`agsc-surface`, `agsc-surface-version`, `agsc-access`, `agsc-visibility`, `agsc-contribute-mode`, `agsc-tombstone`) are Level-independent (V7-06) — a CMS export has no ledger, no `graph.nq` and no build instant, and Level 0 does not ask for one. At Level 2 and above every `digest` REQUIRED by AGSC-06-08, and every `agsc-*` attribute on the `describedby` and `rel#ledger` links, MUST be present. There is no structural difference between the two: `linkset` is the sole member at every Level. [PRD-055 ← D52(3), D55, V3-03]
- **AGSC-06-09** The `linkset` member MUST conform to RFC 9264: an array of link-context objects, each with `anchor` and relation-keyed arrays of objects carrying `href` and optionally `type`. A consumer that cannot obtain the discovery document at the well-known URL of AGSC-06-07 SHOULD try, in order, the home page's `describedby` link whose `type` is `application/linkset+json` (AGSC-06-25) — which names the copy a node MAY serve at a path it controls (AGSC-06-07) — and then `/llms.txt` (AGSC-06-13). This order is informative: a node is not obliged to be reachable by more than the well-known URL, and a reader that finds none of them reports `AGSC-E901`. *(added at rc.6, 2026-09-23, EXT2-02: the discovery-resilience research concluded that the registered name is one door among several, and no rule named a second door, so a consumer meeting a 404 had nowhere to go.)* [PRD-024, RFC 9264]
- **AGSC-06-10** Relation names MUST be either IANA-registered short names — the five this specification itself emits (`describedby`, `alternate`, `license`, `service-doc`, `author`) plus any relation AGSC-06-35 admits for a related-system link (`related`, `service-desc`, `service-meta`, `collection`, `item`, and — added at rc.6, EXT2-03 — `cite-as`) *(amended at rc.5, V9A-03: this rule admitted five names while AGSC-06-35 in the same section requires five more, `config.schema.json` admits all eight and AGSC-09-93 makes `validate-wellknown` check "the names of AGSC-06-10", so the shipped validator would have rejected a legal AGSC-06-35 link)* — or extension URIs of the form `https://w3id.org/agentic-system-core/rel#<name>` with `<name>` ∈ `graph`, `ontology`, `context`, `now`, `skills`, `ledger`, `peer`, (rc.3) `surface`, `contribute`, `access`, and (rc.6) `signature` — of the first six, five have a route in AGSC-06-01 and `ontology` names the vocabulary document of the namespace document site (AGSC-06-06), which a content node does not serve: a node that does not serve it omits the link, and a node that does names its own copy *(stated at rc.6, NS-05: the enumeration of `/ns/` routes was narrowed to the two context copies a content node emits, so "each having a route" stopped being true of `ontology` alone)*; `peer` naming another node's well-known URL for the mutual-conformance test of AGSC-10-12; `surface`, `contribute` and `access` defined in AGSC-11-16, AGSC-11-14 and AGSC-11-20, whose targets are surfaces, contribution endpoints and credential pages and need not be routes of this node; `signature` defined in AGSC-06-08, whose target is a detached signature and need not be a route of this node *(added at rc.6, 2026-09-23, EXT2-07: the IANA link-relation registry holds no relation for a signature, so this specification's own extension form is the only one available)*. `shapes` is NOT a 1.x relation: SHACL shapes stay in the development lane (AGSC-05-24), so no `/ns/shapes.ttl` is published and a relation with no target would be a dangling promise. Unregistered short names MUST NOT be used. Extension **target attributes** (RFC 9264 §4.2.4.3) MUST use the prefix `agsc-` (`agsc-spec-version`, `agsc-generated-at`, `agsc-counts`, `agsc-bundle-hash`, `agsc-bundle-version` (added at rc.6, D113), `agsc-ledger-head`) so that they can never collide with the target attributes RFC 8288 §3.4 defines (`hreflang`, `media`, `title`, `title*`, `type`) or with those RFC 9264 §4.2.4 serialises — no registry of target attributes exists; `digest` is deliberately unprefixed (D82 Q12): RFC 9530 supplies its algorithm token and RFC 9651 its value syntax, and the plain name keeps RFC 9727-style link-set consumers able to read it. Every attribute value is an array of strings. Within one relation's array, link objects are ordered by `href` (code point), and every `href` is absolute — the Bundle base plus the route (V7-27). `type` values are advisory hints (RFC 9264 §4.2.4.1, "Target Attributes Defined by Web Linking", is where the `type` member is specified; RFC 8288 §3.4.1 is where the hint language is — "this is only a hint; for example, it does not override the Content-Type header field of a HTTP response obtained by actually following the link" — corrected at rc.5, V9A-28: §4.2.2 is the link-context object); `application/jsonl` is used for `/ledger.jsonl` and is deliberately unregistered — a reader MUST NOT depend on it. [audit/G §1 RFC 9264 row, RFC 8288, RFC 9530, V2-05, D55]
- **AGSC-06-11** `digest` values are defined once, in AGSC-06-08 (R8); `agsc-ledger-head` MUST be the lowercase hex `hash` of the last entry of the derived ledger of §08 — the head that `verify --ledger` recomputes and compares. A ledger always has at least the trailing `build` entry (AGSC-08-20a), so the head is never undefined where the attribute is required; a Level-0 node publishes no `rel#ledger` link and therefore no head (AGSC-06-08a). `agsc-generated-at` MUST derive from `SOURCE_DATE_EPOCH`. [PRD-005, PRD-024, D44(h) as amended by D48(1) and D55]
- **AGSC-06-12** VoID (`/.well-known/void`, registered 2011) is prior art for dataset discovery and is cited as complementary wherever this specification describes its discovery layer (an editorial commitment, not a conformance requirement — AR2-46). This specification **emits no VoID description**: `graph.jsonld` on the `describedby` link already carries the bundle-level facts (AGSC-06-08), AGSC-06-01's route set is closed, and a SHOULD-emit with no route would be unimplementable. A node that publishes a VoID description independently SHOULD link it from the link set as a second `describedby` link (AGSC-06-09 admits several; AGSC-06-08's "nowhere else" binds the `agsc-*` bundle-facts attributes to the `graph.jsonld` link, not the number of `describedby` targets — V6-B U9). [audit/G §1 VoID row ← V5-3 S3-09]
- **AGSC-06-35** (added 2026-09-17, D82) **Related-system links, OPTIONAL and extensible.** The discovery document MAY carry, in its one link context, links to related discovery documents and systems — an llms.txt v2 file, a VoID or DCAT description, an OKF index, an Agent2Agent Agent Card, an MCP server card, an Agentic Resource Discovery manifest, a publisher-curated LLM context file, an agent-memory, ontology, knowledge-graph or SPARQL endpoint, a runtime or architecture registry — so that any agentic-AI, knowledge, memory or ontology system that this node relates to can be reached from it, and so that new ones can be added without a change to this specification. Such links use **IANA-registered relations only**, chosen by meaning: `describedby` (the target describes this node), `alternate` (the same knowledge in another representation), `related` (a related resource), `service-desc`, `service-doc` and `service-meta` (an interface this node exposes or points at), `collection` and `item` (containment), and `cite-as` (RFC 8574: the target is preferred over this node for the purpose of permanent citation — a concept DOI's landing page, for instance, configured with `type: "text/html"`) *(added at rc.6, 2026-09-23, EXT2-03: `cite-as` is IANA-registered, so this list's registered-names-only condition admits it, and a node that has deposited a release had no way to say which identifier to cite)*. Each MUST carry `type` and MAY carry `profile` (RFC 6906) and `title`. They are configured in `agsc.config.json` as `related[]{rel, href, type, profile?, title?}` (AGSC-01-18; `rel` from the list above, `href` absolute `https:`), emitted in `href` order within each relation (AGSC-06-10), and never derived from content. A reader MUST ignore a related-system link it does not understand; no related-system link affects conformance, any digest, the peer check or the walk (AGSC-11-10 follows `rel#peer` only), and none is ever required at any Level. An unregistered short name (`ard`, `llm-context`, …) MUST NOT be used until IANA registers it — a MINOR adds it then — and a relation not in the list above is `AGSC-E209`. [D82, R60, AR2-01/02/52]

## 6.3 llms.txt

- **AGSC-06-13** (amended at rc.3) `/llms.txt` MUST begin with a single H1 (the Bundle title), then the provenance header of AGSC-06-15 as an HTML comment — a profile of llms.txt v2 (AR2-02) — followed by one blockquote summary, then H2 sections whose bodies are link lists `- [title](url): one-line description`. An `Optional` H2 section MAY hold lower-priority links. [audit/G §1 llms.txt row]
- **AGSC-06-13a** (added at rc.3) **Byte layout of `/llms.txt` and `/llms-full.txt`.** The convention fixes no grammar, so this specification fixes one, and a vector proves it. - **AGSC-06-23** **Tokenizer (normative).** For each item the tokenizer input is, in this order, `title`, `description`, every `tags` value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are **not** token characters. That pin is **16.0.0**, and has been since rc.3; a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. *(The parenthetical "(16.0.0 at rc.3)" was replaced by this sentence at rc.5, V8-115a: labelling a live pin with a release candidate reads as history, and the pin is current.)* A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). ## 6.5 Agent-retrieval chunk export (added at rc.3, 2026-09-16 — D67 Q67 / V-23, D71)

- **AGSC-06-26** A Level ≥ 2 writer MUST emit `/chunks.jsonl`: one JCS-canonical JSON object per LF-terminated line, one line per **chunk**, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the `chunks` surface (AGSC-11-16). This shape holds unless AGSC-06-31 applies, in which case this document is the manifest that rule defines (added at rc.5, V8-95). [D67 Q67, PRD-061, D72 C7]
- **AGSC-06-27** **Boundary rule.** Chunks are cut **after** the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every **ATX** heading of level 2 or 3 (`## `, `### `) that lies **outside any fenced code block**, per CommonMark 0.31.2 (AGSC-02-20) — a `## ` line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted, V7-09), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's `text` ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds `chunks.max_bytes` (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound (V7-44) — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's `text` end without LF and the next begin mid-line (AR2-40). No overlap. The heading is not repeated into continuation chunks. [D72 R-04]
- **AGSC-06-28** **Identifier.** `id` is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by `#chunk-` and the first 16 hex characters of `id`, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [V-23]
- **AGSC-06-29** **Record shape.** Members, all REQUIRED unless marked: `digest` (lowercase-hex SHA-256 of the UTF-8 bytes of `text`), `id`, `iri` (the item IRI), `item` (the slug), `kind` (the item type), `subkind` (OPTIONAL: the concept `kind`, present only on concepts), `license` (`bundle.license_prose`), `links` (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order — AR2-41) in JCS order; OPTIONAL when empty), `ordinal`, `section` (the anchor; empty for chunk 0), `terms` (the Content Use Terms identifier of AGSC-06-18), `text`, `title`, `trust` (always `untrusted` — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), `type` (`text`, or the media type of an attachment chunk, AGSC-06-30). No other member at 1.x; `x-<vendor>-<key>` members MAY follow (AGSC-02-05a). Lines are ordered by item slug (code point), then `section` (code point), then `ordinal` ascending numerically. [PRD-061, AGSC-11-18]
- **AGSC-06-30** **Exclusions and attachments.** Items with `status` `retired` (AGSC-11-22) or `draft`, and items held back by the `releases` switchboard (AGSC-01-20), are excluded — the same set that `search.json` and `/llms.txt` exclude; a cluster contributes one chunk (its description; a cluster without `description` contributes no chunk, V7-09). Each attachment of an item (AGSC-02-98) contributes one chunk whose `type` is the attachment's media type, whose `text` is the attachment's `alt` text for binary media and the file's full text for `image/svg+xml` and other text media, whose `section` is `attachment-<n>` (`<n>` the 1-based index in `attachments[]`) and whose `ordinal` is `0`; a cluster's chunk has `item` = the cluster slug, `iri` = the cluster IRI, `section` empty and `ordinal` `0`. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [D67 Q64, R36]
- **AGSC-06-31** Budgets: `/chunks.jsonl` MUST NOT exceed 8 KB per published item on average; above 500 items a writer MUST shard as `/chunks-<nn>.jsonl` (`<nn>` zero-padded from `01`, each shard the lines of at most 500 items in slug order, no item split across shards) with `/chunks.jsonl` becoming the JCS-canonical manifest `{"bundle_version": <string>, "lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]}` (paths in shard order; `bundle_version` is the content version of AGSC-04-25, added at rc.6 under D113, and is the only member added to this manifest — a chunk line is unchanged, its member set being closed by AGSC-06-29), exactly as AGSC-06-21 shards the index. A chunk line carries no index into any other line, so AGSC-06-21's shard-reading rule has no counterpart here: a reader concatenates the shards in manifest order and needs nothing else (stated at rc.6, FIX29-S1, so that a reader of the two sharding rules does not look for a rule that is deliberately absent). [AGSC-06-21]

## 6.6 JSON-LD context file (added at rc.3 — D67 B2)

- **AGSC-06-32** A Level ≥ 2 writer MUST emit `/ns/context.jsonld`, the target of the `…/rel#context` link (AGSC-06-10) and of the `application/ld+json` branch of `/ns/` negotiation (AGSC-06-06). It MUST be generated from `ontology/agsc.ttl` by a deterministic mapping — every `asc:` term becomes a term definition whose `@id` is its IRI, object properties carry `@type` `@id`, datatype properties carry the `@type` of their declared range, and — because `graph.jsonld` also uses external vocabularies — the prefixes `dcterms`, `prov`, `rdfs`, `schema`, `skos` and `xsd` are defined together with a typed term definition for every external property a rule of §05, §06 or §11 emits (`rdfs:seeAlso` as `@id`, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to `null` (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used — AR2-44); `@version` 1.1 and `@protected` true are set — sorted per AGSC-04-05, and MUST round-trip: expanding `graph.jsonld` with it and re-compacting MUST reproduce `graph.jsonld` **as a value**, and MUST reproduce it byte for byte once the compacted result is serialised in the canonical form of AGSC-04-05 (JCS over NFC strings), which is the form `graph.jsonld` is written in — a JSON-LD processor fixes no member order, so the canonical serialisation is the step that makes the comparison a byte comparison. *(Amended at rc.6, FV29-S1: "byte for byte" was unsatisfiable as written and held on no node of this project; the reference engine's own proof compared canonical forms, so the words and the practice had parted, and a second implementation reading the words would have judged the reference engine non-conforming.)* The term **name** of an `asc:` term is its local name; the term name of an external property is its local name, or its compact IRI (`<prefix>:<local>`) where that local name is also an `asc:` term name or is shared by two external properties. The full context file is therefore a constant of this specification, derived from `ontology/agsc.ttl` and from nothing about a node, and a node's `/ns/context.jsonld` MUST equal it byte for byte (AGSC-05-09). *(Stated at rc.6, NS-04: this rule pinned each term's mapping and never what the term is CALLED, while the member names of `graph.jsonld` are those term names and AGSC-04-24 claims byte-identity for `graph.jsonld` across implementations — three in-house derivations already disagreed, and the released vector `graph-0011` and both published sites use the bare local name, which is what is written down here.)* Released context files are immutable (AGSC-00-16); the versioned copy lives at `/ns/<version>/context.jsonld`. [D67 B2, AGSC-05-09]

## 6.7 Static query fragments (added at rc.3 — D67 A4; SHOULD, sacrificial)

- **AGSC-06-33** A Level ≥ 2 writer SHOULD emit `/graph/fragments/s/<subject-hash>.nq` for every distinct subject IRI and `/graph/fragments/p/<predicate-hash>.nq` for every distinct predicate IRI of `graph.nq` — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus `/graph/fragments/index.json` `{subjects, predicates, generated_at}` — JCS-canonical, `subjects` and `predicates` arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. *(Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.)* [research/29 R6-O1, D72 R-08, A-17]

## 6.8 Dataset vocabularies — VoID and DCAT (informative, added at rc.3 DS-4, 2026-09-16)

VoID is cited as complementary prior art by AGSC-06-12 (a MUST). DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator MAY use to describe a Bundle **as a dataset**; this specification defines no DCAT emission and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to `ontology/agsc.ttl`. Where a publisher emits it, the natural mapping is: the Bundle IRI is a `dcat:Dataset` (and, being a `skos:ConceptScheme`, also the `dcat:themeTaxonomy` of its own catalogue record); `dcterms:title`/`dcterms:description` from `site.title`/`content/index.md`; `dcterms:license` from `bundle.license_prose`; `dcterms:modified` from the build instant; each machine artefact of AGSC-06-01 is a `dcat:Distribution` with `dcat:accessURL` the route, `dcat:mediaType` the served type and `spdx:checksum` the same SHA-256 the link set carries as `digest`; the discovery document itself is the `dcat:landingPage`-adjacent entry point, and the `…/rel#graph` targets are the distributions a triple-store consumer wants. A VoID description (`void:Dataset`, `void:dataDump` = `/graph.nq`, `void:vocabulary` = the `/ns/` IRI) may sit beside it at `/.well-known/void`; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.
