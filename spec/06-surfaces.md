# AGSC-06 — Published surfaces: routes, discovery files, llms.txt

## 6.1 Route set

[PRD-018, PRD-020]
- **AGSC-06-05** Pages MUST NOT reference a third-party origin, load a font, script or image from another host, set a cookie, use browser storage, or emit a beacon — with one exception: the theme control MAY keep the visitor's own theme choice in `localStorage` under the single key `agsc-theme`, whose only values are `light` and `dark`. It MUST write the key only when the visitor chooses a theme and remove it when the visitor chooses the system theme, MUST NOT read, write or send any other stored value, and every page MUST render and work when storage is empty or unavailable; the privacy section of `/legal/` (AGSC-06-18), where the node publishes one, SHOULD say that the choice is kept in the browser, is never sent, and is cleared with the site's data. *(Rationale: the theme control keeps one preference the visitor sets by an explicit choice; the value is never transmitted and identifies no one.)* [PRD-046]
- **AGSC-06-06** `/ns/` conneg is done by the w3id `.htaccess`, mapping `Accept` to a fixed table of same-origin static targets (`text/turtle` → `/ns/agsc.ttl`, `application/ld+json` → `/ns/context.jsonld`, `application/rdf+xml` → `/ns/agsc.rdf`, else the HTML index) — plus the legacy `Accept` aliases `application/x-turtle` (→ Turtle) and `application/json` (→ JSON-LD), which a node MAY accept and no node need send — plus one path rule that sends `/ns/<major>.<minor>.<patch>(/…)?` to the immutable versioned copy of that release before any term rule can capture it (`owl:versionIRI` must resolve). No project-owned server code exists; `/ns/<version>/…` copies are immutable, the pre-release copy `/ns/1.0.0-draft.1/` of AGSC-05-25 included (it is immutable in content, and its directory name is not of the form below, so it is served without the directive, as at 1.0), and a writer MUST serve every file under a version directory `/ns/<major>.<minor>.<patch>/` with `Cache-Control: public, max-age=31536000, immutable`, written into the one `_headers` block of that address (AGSC-06-17), and MUST NOT send that value for `/ns/context.jsonld`, `/ns/agsc.ttl`, `/ns/agsc.rdf`, `/ns/schema/**` or the `/ns/` index, whose bytes change with a release. *(Amended 2026-10-29 for 1.1.0: the immutability of the versioned copies was stated and never sent to a cache; AGSC-11-05 reserved the value `immutable` to digest-named asset paths and is amended with this rule)* [ADR-005]

## 6.2 The well-known file

- **AGSC-06-07** There MUST be exactly one discovery file, `/.well-known/knowledge-linkset` at the root of the node's origin — at 1.0 a node occupies a whole origin (AGSC-01-19) — served as `application/linkset+json` carrying the RFC 9264 §5 profile parameter `profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"`. Where the hosting platform cannot carry a parameter on `Content-Type`, the node MUST instead send the response header `Link: <https://w3id.org/agentic-system-core/profile/agentic-knowledge>; rel="profile"` (RFC 6906); at least one of the two MUST be present, and a reader MUST accept either. No vendor media type is defined, registered or served. Separate manifests MUST NOT be emitted — except the two catalogue files of AGSC-06-42, which are not discovery files of this specification but catalogue entries that point at this one document, are emitted only when `discovery.ai_catalog` is `true`, and which no reader of this specification needs *(Amended 2026-10-29 for 1.1.0: "exactly one discovery file" and "separate manifests MUST NOT be emitted" now admit the opt-in catalogue files, and nothing else)*; a release MAY carry a copy named `knowledge-linkset.json`. `agent-card.json` MUST NOT be published unless the node declares it as the `a2a-card` surface **and** declares a `responder` surface it points at (AGSC-06-34, AGSC-11-16); a card without an endpoint is `AGSC-E210`. The well-known suffix `knowledge-linkset` is **not registered**: its registration under RFC 8615 is asked for in the Internet-Draft `draft-besleaga-agentic-knowledge-wellknown`, which is posted, and no request has been sent to the registry; the Profile URI is registered in the IANA Profile URIs registry under RFC 7284 (First Come First Served) *(Amended 2026-10-02 for 1.0.0: "pending registration" said more than was true)*; the discovery link uses the already-registered relation `describedby` (AGSC-06-25), so no relation is requested. Until the suffix is granted, a node MAY additionally serve the same document at a path it controls, linked with `describedby` and the linkset media type — nothing in this specification says "registered" of the suffix before the registry does *(Amended 2026-10-07 for 1.0.0: IANA has registered the Profile URI in the Profile URIs registry (RFC 7284). This rule said that its registration was "to be requested" and that nothing here says "registered" of the profile before the registry does; the registry now does. The well-known suffix is unchanged: not registered, and no request has been sent to the registry.)*. **The suffix is a single point of substitution**: the reference implementation holds it as one constant (`WELLKNOWN_SUFFIX`) from which the `peers[]` schema pattern, the `_redirects` alias of AGSC-06-17, the vector paths and the rule texts derive, so a refused registration substitutes the next candidate suffix by one MINOR and a regeneration: the new suffix is added and the present path keeps answering with a redirect to it, so no reader that knows only the present path breaks (AGSC-00-14) *(Amended 2026-10-02 for 1.0.0: until `1.0.0-rc.6` this said "by one PATCH", but a new discovery address is an addition, which a MINOR makes)*. The profile URI carries no version: it names the same profile for every version of this specification with the same MAJOR, a discovery document states the version it follows in `agsc-spec-version` (AGSC-06-08), and a new MAJOR that changes what the profile fixes takes a new profile URI. [PRD-024, RFC 9264, RFC 9727 §7.3, RFC 6906]
- **AGSC-06-08** The document is a JSON object — JCS-canonical at Level ≥2 (AGSC-04-04), valid I-JSON at Level 0 (AGSC-06-08a, AGSC-10-02) — whose **sole** top-level member is `linkset` (RFC 9264 §4.2.1); the document MUST NOT carry any other top-level member; the `linkset` array holds exactly one link context object whose `anchor` is the Bundle IRI (AGSC-05-03), its relation-name members ordered as JSON member names (AGSC-04-05). **The anchor is on the origin of the document.** A reader MUST treat a document whose `anchor` is not on the origin of the URL it finally retrieved the document from, after redirects, as not being that node's discovery document (RFC 9264 §9, RFC 8615 §4.3): a validator reports `AGSC-E907`, and a federation walk and the mutual check of AGSC-10-12 skip it as unreadable; a document read from a file has no such origin and is not judged by this sentence. *(Amended 2026-10-02 for 1.0.0: a copy of one node's document served by any other origin passed every check, and a reader would have attributed it to that node.)* Integrity and bundle facts ride on the links as extension target attributes (RFC 9264 §4.2.4.3), whose values are ALWAYS arrays of strings. Every artefact link — a link whose row in the table below says *yes* under `digest` — MUST carry `digest` at Level 2 and above (AGSC-06-08a), a Dictionary with a single member whose key is the RFC 9530 algorithm name `sha-256` and whose value is an RFC 9651 §3.3.5 **Byte Sequence**, serialised per RFC 9651 §4.1 as `sha-256=:<base64>:` and carried as one string in the attribute's array, over the canonical bytes of the target. Bundle-level facts ride on the anchor's `describedby` link to `graph.jsonld` and nowhere else: `agsc-spec-version` (one value), `agsc-generated-at` (one value, an AGSC-04-10 instant derived from `SOURCE_DATE_EPOCH`), `agsc-counts` (one `"<type-plural>=<n>"` string per item type, in code-point order of the type name, counted over the published set — release-gated, draft and retired items excluded, AGSC-06-30), `agsc-bundle-hash` (the AGSC-04 bundle hash, RFC 9530 syntax), and `agsc-bundle-version` (one value, the content version of AGSC-04-25: the hash says whether two nodes hold the same content and never what the publisher calls that content, so a reader that wants to cite or compare releases needs both). The ledger is the link `https://w3id.org/agentic-system-core/rel#ledger`, carrying `digest` and `agsc-ledger-head` (one value, the lowercase hex head of the derived ledger of §08). A node MAY carry one further link whose relation is `https://w3id.org/agentic-system-core/rel#signature` (AGSC-06-10) and whose target is a detached signature over the canonical bytes of this document. At 1.x no rule pins the signature format, no Level requires the link, it affects no digest, no claim and no walk, and a reader MUST ignore it if present. *(Non-normative: the digests of this rule establish that the bytes are the bytes the publisher hashed; they establish nothing about who the publisher is. The trust anchor at 1.x is the origin's TLS certificate and DNS name, and a publisher who needs more publishes the optional signature. The nearest comparator, the Agent2Agent Agent Card, makes a signature over its canonical card optional ("Agent Cards MAY be digitally signed", A2A §8.4, read 2026-09-16 and quoted in `docs/SECURITY-CONSIDERATIONS.md` §2); this specification keeps its own optional for the same reason and one more — a static node has no key custody — and the reasoning is written here rather than left to inference. No IANA-registered relation exists for a signature — the registry was read on 2026-09-23 and holds none — so the link can only take this specification's own extension-URI form, and AGSC-06-35's registered-names-only list cannot admit it.)* *(Amended 2026-10-02 for 1.0.0: the table below names every link the document carries, when, and which of them carry `digest`; until then "artefact link" was not defined.)*

- **AGSC-06-08a** At **Level 0** (AGSC-10-02) the document is the **same** link set with every `digest` and every `agsc-*` attribute of AGSC-06-08 (`agsc-spec-version`, `agsc-generated-at`, `agsc-counts`, `agsc-bundle-hash`, `agsc-bundle-version` and `agsc-ledger-head`, and from 1.1 `agsc-chunk-count`, `agsc-chunk-set` and `agsc-ledger-length`) omitted — the §11 attributes (`agsc-surface`, `agsc-surface-version`, `agsc-access`, `agsc-visibility`, `agsc-contribute-mode`, `agsc-tombstone`) are Level-independent — a CMS export has no ledger, no `graph.nq` and no build instant, and Level 0 does not ask for one. At Level 2 and above every `digest` REQUIRED by AGSC-06-08, and every `agsc-*` attribute on the `describedby` and `rel#ledger` links, MUST be present. There is no structural difference between the two: `linkset` is the sole member at every Level. [PRD-055]
- **AGSC-06-09** The `linkset` member MUST conform to RFC 9264: an array of link-context objects, each with `anchor` and relation-keyed arrays of objects carrying `href` and optionally `type`. A consumer that cannot obtain the discovery document at the well-known URL of AGSC-06-07 SHOULD try, in order, the home page's `describedby` link whose `type` is `application/linkset+json` (AGSC-06-25) — which names the copy a node MAY serve at a path it controls (AGSC-06-07) — and then `/llms.txt` (AGSC-06-13). This order is informative: a node is not obliged to be reachable by more than the well-known URL, and a reader that finds none of them reports `AGSC-E901`. *(Rationale: the well-known name is one door among several, and a consumer meeting a 404 needs a second door.)* [PRD-024, RFC 9264]

## 6.4 Machine surfaces and headers

- **AGSC-06-16** `search.json` MUST be a prebuilt inverted index `{terms:{token:[docIndex…]}, docs:[{slug,title,description,cluster}]}` requiring no runtime dependency. `docs[]` MUST be ordered by slug, each posting list MUST be ascending `docIndex` values without repetition, and the `terms` member names MUST be ordered as JSON member names per AGSC-04-05. [PRD-014]
- **AGSC-06-23** **Tokenizer (normative).** For each item the tokenizer input is, in this order, `title`, `description`, every `tags` value and the body with fenced code blocks removed. The input MUST be NFC-normalized, then ASCII-lower-cased (only U+0041–U+005A are mapped; no locale casing, no case folding of non-ASCII), then split at every run of characters that are **not** token characters. A token character is `[a-z0-9]` or a character whose Unicode General_Category is `L*` (any letter), `Nd` (decimal digit) or `M*` (combining mark, so Devanagari and Thai words are not split); every other character — including `No`/`Nl` forms such as `²` and `Ⅷ`, and `Lo`-adjacent symbols — is a boundary. Non-ASCII letters and digits are kept code-point-wise and never transliterated. The General_Category table is that of the Unicode version pinned by AGSC-04-22. That pin is **16.0.0**; a port using another version MUST state it in its conformance claim, since that is the only remaining source of divergence. A token shorter than 2 Unicode code points MUST be dropped (AGSC-02-24). - **AGSC-06-18** One licence policy is expressed in exactly **three** machine-readable dialects at 1.x, and no more: the per-crawler `User-agent`/`Disallow` groups of `robots.txt` (RFC 9309); the TDMRep policy at `/.well-known/tdmrep.json` (the TDM Reservation Protocol well-known location, and the **only** route that carries it — the duplicate copy at `/tdmrep.json` is not emitted); and the `schema:license`/`schema:usageInfo` members of the JSON-LD views together with `llms.txt`. `rsl.xml` and the aipref `Content-Usage` field are **not** emitted at 1.x, and no rule, route or claim may assert them. A `Content-Signal` line in a `robots.txt` group — the reference engine writes one in every group — is an optional "other record" of RFC 9309 §2.2.4, which a crawler may interpret or ignore: it restates the same policy for the crawlers that read it, is not counted as a dialect and is compared with nothing. The three dialects express one policy at three levels of precision, and only what is **comparable** is compared: a TDMRep `tdm-reservation` of `1` MUST be accompanied by a `robots.txt` group `User-agent: <token>` with `Disallow: /` for every product token (RFC 9309 §2.2.1) of `site.tdm_crawlers[]` (AGSC-01-18), and by a `schema:usageInfo` naming the Content Use Terms; a disagreement on those three comparable facts — a token of the list with no such group, or a reservation with no such `schema:usageInfo` — MUST fail the build with `AGSC-E202`, and nothing else is compared. `site.tdm_crawlers[]` is the **publisher's own, maintained** list of the product tokens whose operators state that they collect content in order to train a machine-learning model; it is configuration and never a constant of this specification, because vendors rename tokens and add them and a list frozen into a standard goes stale where it matters most. A writer MUST emit one such group per token, in the order the configuration states them and before the `User-agent: *` group, and MUST NOT emit a `Disallow` for any token the list does not name — a fetch made on a person's behalf, and a search crawler, stay invited, which is what keeps a node readable by the agents it exists for. ## 6.5 Agent-retrieval chunk export

- **AGSC-06-26** A Level ≥ 2 writer MUST emit `/chunks.jsonl`: one JCS-canonical JSON object per LF-terminated line, one line per **chunk**, UTF-8, NFC, no blank lines, one trailing LF. The file is the Bundle's agent-retrieval export: a stable, citable, pre-split unit set with provenance, so that any agent can use the Bundle as remote memory without re-chunking, guessing boundaries or inventing identifiers. Embeddings are out of scope; the record is embedding-ready. The file is declared as the `chunks` surface (AGSC-11-16). This shape holds unless AGSC-06-31 applies, in which case this document is the manifest that rule defines. [PRD-061]
- **AGSC-06-27** **Boundary rule.** Chunks are cut **after** the AGSC-04-07 normalisation of the item body; fenced code is NOT removed (code stays in its chunk). Cut 1: at every **ATX** heading of level 2 or 3 (`## `, `### `) that lies **outside any fenced code block**, per CommonMark 0.31.2 (AGSC-02-20) — a `## ` line inside a fence is content, and setext headings are not cut points — the text before the first such heading is chunk 0 (an empty chunk 0 — a body that begins with a cut heading, or an empty body — is not emitted), and each heading with its following text is one chunk, the heading line included. The blank line(s) immediately preceding a cut belong to neither chunk, so a chunk's `text` ends with exactly one LF and never begins with one. Cut 2: a chunk whose UTF-8 byte length exceeds `chunks.max_bytes` (AGSC-11-01; default 4096, maximum 65536) is split at the last paragraph boundary (a blank line, i.e. two consecutive LFs) at or before the bound — the chunk's byte length, excluding the separating blank line, MUST NOT exceed the bound — repeatedly; a single paragraph longer than the bound is split at the last LF at or before the bound, and, failing that, at the bound on a code-point boundary — only in that last case may a chunk's `text` end without LF and the next begin mid-line. No overlap. The heading is not repeated into continuation chunks. [design]
- **AGSC-06-28** **Identifier.** `id` is the lowercase-hex SHA-256 of the UTF-8 bytes of the item IRI, then one U+0000 (NUL) byte, then the section path, then one U+0000 (NUL) byte, then the ordinal in decimal — where the section path is the AGSC-03-13 anchor of the chunk's heading (the empty string for chunk 0) and the ordinal is the zero-based index of the chunk within that section after Cut 2. Two conforming writers therefore derive identical ids from identical sources; an agent cites a chunk back as the item IRI followed by `#chunk-` and the first 16 hex characters of `id`, which a page MUST render as an in-page anchor on the chunk's heading (the top of the page for chunk 0). [design]
- **AGSC-06-29** **Record shape.** Members, all REQUIRED unless marked: `digest` (lowercase-hex SHA-256, FIPS 180-4, of the UTF-8 bytes of the decoded `text` string exactly as the `text` member states it — not of the JSON-escaped line, not of the record and not of any other member), `id`, `iri` (the item IRI), `item` (the slug), `kind` (the item type), `subkind` (OPTIONAL: the concept `kind`, present only on concepts), `license` (`bundle.license_prose`), `links` (the item's authored Links as an object of key → slug arrays (anchors stripped; each array in code-point order) in JCS order; a target naming an item excluded by AGSC-06-30 is dropped from its array and a key emptied by that drop is omitted (the exclusion every other surface applies); OPTIONAL when empty), `ordinal`, `section` (the anchor; empty for chunk 0), `terms` (the Content Use Terms identifier of AGSC-06-18), `text`, `title`, `trust` (always `untrusted` — the value an agent MUST attach when the text re-enters a model, AGSC-08-18), `type` (`text`, or the media type of an attachment chunk, AGSC-06-30). A 1.0 writer emits no other member; from 1.1 a writer also emits, each only under its condition: `abstract` (the item's own `description`, copied unchanged, never written by a model, present whenever the item has a non-empty `description` and omitted otherwise; every chunk of the item carries it, a cluster's chunk included, whose `text` already is the description; its bytes count toward the budget of AGSC-06-31), `license_url` (the licence URL of AGSC-06-44, omitted when the node has none) and `content_digest` (OPTIONAL, present only when `chunks.content_digest` is `true`, default `false`: the SHA-256 of the same bytes as `digest` in the RFC 9530 form `sha-256=:<base64>:` (the standard base64 alphabet with `=` padding), a Byte Sequence of RFC 9651, so that a client with an RFC 9530 library needs no conversion; it never replaces `digest` and the two MUST name the same hash); `x-<vendor>-<key>` members MAY follow (AGSC-02-05a), a later MINOR may add members, and a reader MUST ignore a member it does not know (AGSC-00-21). Lines are ordered by item slug (code point), then `section` (code point), then `ordinal` ascending numerically. *(Amended 2026-10-29 for 1.1.0: the algorithm and the covered bytes of `digest` are named, and `abstract`, `license_url` and `content_digest` are added as optional members, which a 1.0 reader ignores (AGSC-00-21); for an item with a description every chunk line of that item changes by the `abstract` member)* [PRD-061, AGSC-11-18]
- **AGSC-06-30** **Exclusions and attachments.** Items with `status` `retired` (AGSC-11-22) or `draft`, and items held back by the `releases` switchboard (AGSC-01-20), are excluded — the same set that `search.json` and `/llms.txt` exclude; a cluster contributes one chunk (its description; a cluster without `description` contributes no chunk). Each attachment of an item (AGSC-02-98) contributes one chunk whose `type` is the attachment's media type, whose `text` is the attachment's `alt` text for binary media and the file's full text for `image/svg+xml` and other text media, whose `section` is `attachment-<n>` (`<n>` the 1-based index in `attachments[]`) and whose `ordinal` is `0`; a cluster's chunk has `item` = the cluster slug, `iri` = the cluster IRI, `section` empty and `ordinal` `0`. The in-page anchor of AGSC-06-28 is required only for chunks that begin with a heading; every other chunk is cited at the top of its page. Peer-derived content never appears in a node's own export (AGSC-11-11). [design]
- **AGSC-06-31** Budgets: `/chunks.jsonl` SHOULD NOT exceed 8 KB per published item on average (a bound that a valid input can exceed, since a long item body is chunked whole, is advisory from 1.1: a build reports no finding for it, and the sharding below is what bounds the size of one file); above 500 items a writer MUST shard as `/chunks-<nn>.jsonl` (`<nn>` zero-padded from `01`, each shard the lines of at most 500 items in slug order, no item split across shards) with `/chunks.jsonl` becoming the JCS-canonical manifest `{"bundle_version": <string>, "lines_total": <integer>, "shards": ["/chunks-01.jsonl", …]}` (paths in shard order; `bundle_version` is the content version of AGSC-04-25, and a chunk line does not carry it, its member set being closed by AGSC-06-29), exactly as AGSC-06-21 shards the index. A chunk line carries no index into any other line, so AGSC-06-21's shard-reading rule has no counterpart here: a reader concatenates the shards in manifest order and needs nothing else (so that a reader of the two sharding rules does not look for a rule that is deliberately absent). The `digest`, the count and the chunk-set commitment of AGSC-06-44 are those of the lines of all shards read in manifest order, and the `digest` is that of the manifest file when the export is sharded. *(Amended 2026-10-29 for 1.1.0: the manifest is the file the surface digest covers when the export is sharded)* *(Amended 2026-10-29 for 1.1.0: the average budget is advisory, as AGSC-04-03 says, because an item body of any admitted length produces its chunks)* [AGSC-06-21]
- **AGSC-06-37** **Tabular chunk index.** A Level ≥ 2 writer MAY emit `/chunks-index.toon`, a tabular index of `/chunks.jsonl` in the TOON format (`@toon-format/toon` 4.1.1, specification 4.1, the tabular form of its §9.3). The file is UTF-8, NFC, LF-terminated, with one trailing LF (AGSC-04-07), and consists of the header `chunks[<n>]{id,item,kind,section,ordinal,title,digest}:` — `<n>` the number of chunk lines — followed by one row for each chunk line of `/chunks.jsonl`, in the same order, whose columns are `id` and `digest` cut to their first 16 hexadecimal characters, and `item`, `kind`, `section`, `ordinal` and `title` as the record states them. Each row is indented by two spaces and its values are joined by `,`; a value is written bare unless the quoting rule of TOON specification 4.1 requires quotes, in which case it is written in double quotes with `\"` and `\\` escaped — an empty string is `""`, and a string that contains `,`, `:`, `"` or `\`, a control character, a leading or trailing space, or that reads as a number, `true`, `false` or `null`, is quoted; `ordinal` is written in decimal without leading zeros (the case `chk-0010` shows rows). A Bundle with no chunk line gets the header with `<n>` of `0` and no row, never an empty file. The index is regenerated with `/chunks.jsonl`, never differs from it in rows or in order, and carries no member that the records lack. It is emitted only when the published set holds at most 500 items: above that the file is not emitted, because `/chunks.jsonl` is itself sharded (AGSC-06-31) and the index has no shard of its own. It is announced, if at all, by a `related[]` link (AGSC-06-35) and by no surface name and no `rel#` relation, so the closed lists of AGSC-11-16 and AGSC-06-10 gain nothing, and its absence is never a fault at any Level (AGSC-10-04). The cut `digest` is a locator only: a reader that cites a chunk checks the full `digest` of the record (AGSC-06-29). *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the export adapter `llm-context` wrote this file beside the node and the main site served it under `/exports/`; the route, the header row and the size condition are fixed here)* [design]
- **AGSC-06-44** **Chunk integrity: the digest on the surface link, the chunk-set commitment, the licence URL and the freshness of the ledger.** From 1.1 a Level ≥ 2 writer, on a node that is not `restricted` (AGSC-11-20), MUST give the `rel#surface` link whose `agsc-surface` is `chunks` (AGSC-11-16): a `digest` of the form of AGSC-06-08 over the canonical bytes of `/chunks.jsonl`, which is the manifest file when the export is sharded (AGSC-06-31); `agsc-chunk-count`, one value, the decimal number of chunk lines across all shards; and `agsc-chunk-set`, one value in the form of `digest`, the SHA-256 over the concatenation, in file order and in shard order, of the `id` of every chunk line, each written as its 64 lowercase hexadecimal characters followed by one LF (0x0A) — for an export with no line, the SHA-256 of the empty byte string. A consumer that holds the lines recomputes the count and the commitment and so finds a chunk that was dropped or added; the `digest` of each record finds a text that was changed (AGSC-06-29); none of the three says who published the file (AGSC-06-08). `validate-wellknown` at `--level 2` and above recomputes the three over the fetched file and requires them of a document whose `agsc-spec-version` is 1.1.0 or later; it accepts their absence in an earlier document. The `rel#ledger` link MAY carry `agsc-ledger-length`, one value, the decimal number of entries of the derived ledger (AGSC-08-20a), beside `agsc-ledger-head`. The **licence URL** of a node is, in this order: `bundle.license_url` when configured (AGSC-01-18; a URL that names a specific version of the licence, such as the address of version 4.0 of a Creative Commons licence and not the address that names the licence without a version); else, when `bundle.license_prose` is the Content Use Terms identifier or is absent and the node emits `/legal/` (AGSC-06-18), the absolute URL of `/legal/`; else none. Every chunk of a node that has one carries it as `license_url` (AGSC-06-29), and the same URL is the `license` link of AGSC-06-40 and the `license` of AGSC-06-41; `license` and `terms` are unchanged. A consumer SHOULD verify the `digest` of a chunk, and its `id`, before it hands the chunk's text to a model, and a consumer that keeps the last `agsc-ledger-head` it accepted SHOULD accept a later discovery document only when that head is still the `hash` of an entry of the ledger it then fetches (AGSC-08-23) — a ledger that no longer holds it was rolled back or rewritten — and MAY compare `agsc-ledger-length` first. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: a chunk could be altered, dropped or served stale without a statement that a reader could check; these four additions give the surface link, the set, the licence and the ledger a checkable form)* [design, RFC 9530, RFC 9651]
- **AGSC-06-45** **A chunk's text begins with a line that is not blank.** No chunk's `text` begins with a line feed: the text of chunk 0 (the text before the first heading that Cut 1 of AGSC-06-27 cuts at) starts at the first line that is not blank, and so does the text of every other chunk, the pieces that Cut 2 produces included; a line is blank when it is empty or holds only U+0020 and U+0009. Blank lines inside a text are kept, and nothing else of AGSC-06-27 changes: a text still ends with exactly one line feed, except where one paragraph is split in the middle of a line. AGSC-06-27 has said since 1.0 that a chunk never begins with a line feed, and a 1.0 writer kept the blank lines that began a body in chunk 0; so for an item whose body begins with a blank line the `text` and the `digest` of chunk 0 in 1.1 differ from those of 1.0, and its `id` does not (AGSC-06-28). A body that begins with a heading that Cut 1 cuts at, or with a non-blank line, gives the same chunks as in 1.0. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: stated as a rule of its own, and not as a correction, so that the one change of chunk-0 digests that 1.1 makes to a Bundle of 1.0 is named here and in the change log)* [design, AGSC-06-27]

## 6.6 JSON-LD context file

- **AGSC-06-32** A Level ≥ 2 writer MUST emit `/ns/context.jsonld`, the target of the `…/rel#context` link (AGSC-06-10) and of the `application/ld+json` branch of `/ns/` negotiation (AGSC-06-06). It MUST be generated from the vocabulary file of the context version (`ontology/agsc.ttl` as it stood at version 1.0.0, AGSC-05-09; a term the file gained later, such as `asc:warrant`, is not in it) by a deterministic mapping — every `asc:` term of that file becomes a term definition whose `@id` is its IRI, object properties carry `@type` `@id`, datatype properties carry the `@type` of their declared range, and — because `graph.jsonld` also uses external vocabularies — the prefixes `dcterms`, `prov`, `rdfs`, `schema`, `skos` and `xsd` are defined together with a term definition for every external property a rule of §05, §06 or §11 emits (`rdfs:seeAlso` as `@id`, the SKOS, DCTerms, PROV and schema.org properties named in AGSC-05-14…20, 05-27, 05-29, 06-18 and 11-12); no term is ever mapped to `null` (a null term definition, which JSON-LD 1.1 keeps as a blocked term so that it can never be used); `@version` 1.1 and `@protected` true are set — sorted per AGSC-04-05, and MUST round-trip: expanding `graph.jsonld` with it and re-compacting MUST reproduce `graph.jsonld` **as a value**, and MUST reproduce it byte for byte once the compacted result is serialised in the canonical form of AGSC-04-05 (JCS over NFC strings), which is the form `graph.jsonld` is written in — a JSON-LD processor fixes no member order, so the canonical serialisation is the step that makes the comparison a byte comparison. The term **name** of an `asc:` term is its local name; the term name of an external property is its local name, or its compact IRI (`<prefix>:<local>`) where that local name is also an `asc:` term name or is shared by two external properties. The full context file is therefore a constant of this specification, derived from the vocabulary file of the context version and from nothing about a node, and a node's `/ns/context.jsonld` MUST equal it byte for byte (AGSC-05-09). *(Rationale: the member names of `graph.jsonld` are these term names, and AGSC-04-24 claims byte-identity for `graph.jsonld` across implementations; the vector `graph-0011` uses the bare local name.)* Released context files are immutable (AGSC-00-16); the versioned copy lives at `/ns/<context-version>/context.jsonld`, `<context-version>` being the **context version** of AGSC-05-09 — `1.0.0` at every version 1.x of this specification, and not the ontology version, which moves with the vocabulary file — and the constant that a node's `/ns/context.jsonld` MUST equal is the context file of that version. *(Amended 2026-10-29 for 1.1.0: the address names the context version and not the ontology version, so that the `@context` address and the bytes of a `graph.jsonld` of 1.0 do not change when the vocabulary file gains annotations or terms (AGSC-05-09, case `graph-0043`))* *(Amended 2026-10-10 for 1.0.0: the word "typed" is dropped; not every external term definition carries an `@type`.)* [AGSC-05-09]

## 6.7 Static query fragments (SHOULD, sacrificial)

- **AGSC-06-33** A Level ≥ 2 writer SHOULD emit `/graph/fragments/s/<subject-hash>.nq` for every distinct subject IRI and `/graph/fragments/p/<predicate-hash>.nq` for every distinct predicate IRI of `graph.nq` — each file the byte-sorted N-Quads lines sharing that term, the hash being the first 16 hex characters of the SHA-256 of the IRI — plus `/graph/fragments/index.json` `{subjects, predicates, generated_at}` — JCS-canonical, `subjects` and `predicates` arrays of file paths in code-point order. Object fragments are NOT emitted at 1.x. A writer that does not emit fragments MUST NOT emit the index. *(Non-normative: a static subset of the Triple Pattern Fragments interface at the dump end of the Linked Data Fragments spectrum; counts and controls are omitted at 1.x.)* [design]

## 6.8 Dataset vocabularies — VoID and DCAT (informative)

VoID is cited as complementary prior art by AGSC-06-12, a requirement. DCAT 3 (W3C Recommendation, 22 August 2024) is the catalogue vocabulary a publisher or an aggregator may use to describe a Bundle **as a dataset**; this specification defines no DCAT emission and no rule depends on one, so the mapping below is a courtesy to catalogue maintainers and adds no term to `ontology/agsc.ttl`. Where a publisher emits it, the natural mapping is: the Bundle IRI is a `dcat:Dataset` (and, being a `skos:ConceptScheme`, also the `dcat:themeTaxonomy` of its own catalogue record); `dcterms:title`/`dcterms:description` from `site.title`/`content/index.md`; `dcterms:license` from `bundle.license_prose`; `dcterms:modified` from the build instant; each machine artefact of AGSC-06-01 is a `dcat:Distribution` with `dcat:accessURL` the route, `dcat:mediaType` the served type and `spdx:checksum` the same SHA-256 the link set carries as `digest`; the discovery document itself is the `dcat:landingPage`-adjacent entry point, and the `…/rel#graph` targets are the distributions a triple-store consumer wants. A VoID description (`void:Dataset`, `void:dataDump` = `/graph.nq`, `void:vocabulary` = the `/ns/` IRI) may sit beside it at `/.well-known/void`; both are optional, both point at artefacts this specification already pins, and neither is a conformance target at 1.x.

## 6.9 Graph view and query page (1.1)

- **AGSC-06-38** **Graph view, relations table and backlinks.** An item page and a cluster page SHOULD show the neighbourhood of the item or the cluster as an inline SVG figure, drawn from published items only, with a **relations table** beside it as its text equivalent (AGSC-06-20). The table has one row for each relation key that links the item and another item, in either direction, and each row gives the key, its direction (outgoing or incoming), the other item's title as a link to its page, and the plain meaning of the key, taken from the `Meaning` column of the table of AGSC-03-01. The incoming rows are the **backlinks** of the item: every published item that links to it by one of the fourteen keys; a link written inside a body is not a backlink. The figure draws at most 24 neighbours, the first 24 rows of the relations table in its order, and the table says how many more there are. Published means that AGSC-06-30 does not exclude the item: an item that is a draft, retired or held back by the `releases` switchboard is neither drawn nor named, and a link to it is neither a row nor a backlink. A writer that draws the figure MUST also write the table, and MUST keep the figure inside the SVG rules of AGSC-02-13 and AGSC-01-07 and the page inside the budget of AGSC-06-21; a relation filter needs no script, and no route is added. A cluster page draws its members and the links among them the same way, and `/clusters/` carries the overview of all clusters and a legend of the fourteen keys with their meanings. On a node that uses the domain layer (AGSC-01-41: a site vocabulary file is present), for the items that carry the keys `domain_type`, `domain_role`, `domain_context` or `warrant` (AGSC-02-25, AGSC-05-40), the relations table of an item page MUST also show, in each row, the other item's domain type and context, and the page MUST show the item's own domain type, role, context and warrant in a definition list under the table, each with the label that the site vocabulary gives it; a node that does not use the layer shows none of these, and its pages differ from those of 1.0 only by the figure, the table and the backlinks. HTML pages are not byte-pinned (AGSC-04-24), and the figure and the table are views added to the page, not changes to a machine file. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the 1.0 page listed the links of an item and nothing of what links to it; the figure, the table with the meanings of the keys and the backlinks are added, and the domain-layer parts are written with the layer itself)* [design, AGSC-06-30]
- **AGSC-06-39** **Query page.** Unless `site.query_page` is `false` (AGSC-01-18; the default is `true`), a writer that serves `/graph.nq` MUST emit `/query/`, a page on which a visitor writes a query in SPARQL 1.1 (W3C Recommendation of 21 March 2013) and runs it against the node's own published graph, in the visitor's browser and nowhere else; no server takes part. The page MUST: (a) load `/graph.nq` of the same node into an in-browser RDF store, answer `SELECT`, `ASK`, `CONSTRUCT` and `DESCRIBE`, refuse an update and a `SERVICE` clause, and request no address outside the origin of the node; (b) offer, as named examples that fill the editor, the ten questions that the graph must answer (AGSC-05-34), each with the query by which the question is defined, and, on a node that declares competency questions of its own (AGSC-05-41), those too; (c) show a result as a table, and a `CONSTRUCT`, `DESCRIBE` or three-column result also as a graph picture; (d) offer the result for download as CSV and as JSON, in the formats of the W3C Recommendations "SPARQL 1.1 Query Results CSV and TSV Formats" and "SPARQL 1.1 Query Results JSON Format" (both of 21 March 2013); (e) make each query shareable as a link whose fragment (the part after `#`) holds the query text, so that no request to any server carries it, and put the query of such a link into the editor, running it only when the visitor asks; (f) carry a vocabulary explorer that lists the classes and the fourteen relation keys with their plain meaning (the `Meaning` column of AGSC-03-01) and, on a node with a site vocabulary (AGSC-05-38), its classes and relations. The page keeps AGSC-06-05 — it stores nothing, not even the last query, and sends nothing — and AGSC-06-20 (WCAG 2.2 AA, every control operable from the keyboard). The HTML of `/query/` keeps the page budget of AGSC-06-21; the query engine and its licence text are same-origin page assets of the page (AGSC-06-01), outside that budget, and are the files of one release of an engine whose licence allows their redistribution; this specification names no engine, and the conformance case checks the rules (a) to (f) through the page's markup and the content security policy of AGSC-06-17 only (`build-0030`), not the engine. The content security policy of `/query/` and of the files under it is the policy of AGSC-06-17; a writer whose engine is compiled to WebAssembly MAY add `'wasm-unsafe-eval'` to its `script-src`, and MUST NOT add `'unsafe-eval'`, `'unsafe-inline'`, a host source, or any loosening of `default-src`, `style-src`, `img-src` or `connect-src`. A node with `site.query_page` set to `false` emits no `/query/`, no file under it and no link to it. A Bundle of 1.0 built by a 1.1 writer with the default gains `/query/` and its assets, an entry for it in `/sitemap.xml` (AGSC-06-19), a navigation link on every generated page, and the `_headers` block of the page; no other file changes. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: a visitor can ask the published graph a question without installing anything and without a server; the switch lets a node keep the file set of 1.0, and a Bundle that sets it SHOULD declare a `spec_version` of 1.1.0 or later (AGSC-01-18))* [design, AGSC-06-17]

## 6.10 Signposting, dataset fields, catalogue files and page relations (1.1)

- **AGSC-06-40** **FAIR Signposting links on the home page.** A Level ≥ 2 writer MUST send, in the `Link` header of `/`, the typed links that FAIR Signposting (signposting.org/FAIR, read 2026-10-29) asks of a landing page at its Level 1, so that a client that reads only headers finds the identifier, the licence, the metadata and the content files: `cite-as`, exactly one, whose target is the `href` of the first `related[]` link of relation `cite-as` in `href` order (AGSC-06-35) or, without one, the Bundle IRI; `type`, two, `https://schema.org/Dataset` and then `https://schema.org/AboutPage`; `describedby`, the discovery document with `type="application/linkset+json"` (AGSC-06-25) and `/graph.jsonld` with `type="application/ld+json"`; `item`, `/graph.nq`, `/graph.ttl` and, where the node serves it, `/chunks.jsonl`, each with its `type`; `license`, the licence URL of AGSC-06-44 when the node has one; and `linkset`, the discovery document with `type="application/linkset+json"`. The targets on the node itself are root-relative, as in AGSC-06-25, while the targets of `cite-as` and `license` are absolute URLs, and the values are written into the one `_headers` block of `/` (AGSC-06-17), as one `Link` field with comma-separated values or as one field for each. A `restricted` node (AGSC-11-20) sends `cite-as`, `type`, `describedby`, `linkset` and `license`, and no `item`. This rule claims the landing-page half of Signposting Level 1 (section 2.1.1) and the `linkset` link; the `collection` and `describes` links that section 2.1.2 asks for on the content and metadata files themselves are not sent, and the discovery document does not carry every landing-page link that Level 2 asks for. Informative example of one value: `</.well-known/knowledge-linkset>; rel="describedby"; type="application/linkset+json"`; the case `disc-0026` compares the links as a set and does not pin their order or the spacing. `validate-wellknown`, given a URL, reads the `Link` header of `/` and checks that it carries the `describedby` link of AGSC-06-25 whose target is the discovery document; its absence is reported as a warning under `AGSC-E202`, because AGSC-06-25 makes the header a SHOULD. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: FAIR Signposting asks for typed links in the headers of a landing page; the discovery document already exists and is named by `linkset`, and the checker did not look at the header)* [design, RFC 8288, RFC 9264]
- **AGSC-06-41** **Dataset fields of the home page.** The `Dataset` JSON-LD block of the home page (AGSC-06-19) carries from 1.1, besides `name`, `description` and `url`: `license`, the licence URL of AGSC-06-44, omitted when the node has none; `creator`, a `Person` with a `name` and, where an ORCID iD is configured, a `sameAs` that holds `https://orcid.org/` followed by the iD — taken from `bundle.creator` (`name` and OPTIONAL `orcid`), else from `site.author` with `site.author_orcid` (AGSC-01-18) — omitted when neither is configured; `isAccessibleForFree`, `true` on a node that is not `restricted`; and `distribution`, one `DataDownload` for each of `/graph.jsonld`, `/graph.ttl`, `/graph.nq`, `/chunks.jsonl` (its manifest when sharded) and `/.well-known/knowledge-linkset` that the node serves, in that order, with an absolute `contentUrl` and an `encodingFormat` (the type the file is served with, and `application/jsonl` for the chunks). The block names the PROV-O vocabulary (W3C Recommendation of 30 April 2013) with the prefix `prov` in its `@context` and carries `prov:generatedAtTime`, the build instant (AGSC-04-09), and `prov:wasAttributedTo`, the same `Person` object as `creator`; these two terms appear in this block and in no other place — not in `graph.jsonld`, `graph.ttl` or `graph.nq`, not in `pages/*.jsonld`, and not in the block of any other page — so that the graph files and the `@context` address of 1.0 do not change. The block of a `restricted` node holds no `distribution`, its files being gated. The fields follow the recommendations of the Google Search Central guide for datasets (last updated 2026-09-08, read 2026-10-29): a `license` URL that names a specific version of the licence and an ORCID iD for a person; a `description` shorter than 50 characters, which Google ignores, is reported as the warning `AGSC-E202`; the `encodingFormat` `application/jsonl` of the chunks is not a registered media type (AGSC-06-17); no other index page changes. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: Dataset search reads the license, the creator and the distribution; the 1.0 block held a name, a description and a URL only. The PROV-O terms are confined to this block so that the graph bytes stay those of 1.0)* [design, schema.org]
- **AGSC-06-42** **AI-catalogue files (opt-in; both formats are proposals).** A node whose configuration sets `discovery.ai_catalog` to `true` (AGSC-01-18; the default is `false`) MUST emit `/.well-known/ard.json` and `/.well-known/ai-catalog.json`, and a node that leaves it `false` MUST NOT emit either. Both formats are proposals, not standards: the Agentic Resource Discovery manifest, version 0.91, status "Proposal", dated 26 August 2026 (agenticresourcediscovery.org/spec), and the AI Catalog draft, `specVersion` "1.0", undated (ai-catalog.io/spec), both read 2026-10-29; neither suffix is in the IANA registry of well-known URIs (read 2026-10-29). Each file is a JCS-canonical (AGSC-04-05) JSON document with one trailing LF, served as a public artefact with the headers of AGSC-11-03 and the media type `application/ai-catalog+json` for `ai-catalog.json` and `application/json` for `ard.json`. `ard.json` is `{"entries":[…]}` and `ai-catalog.json` is `{"entries":[…],"specVersion":"1.0"}`. The entries are, in `identifier` order, one for the discovery document of AGSC-06-07 and, when AGSC-06-34 emits a card, one for the card. An entry has: `identifier`, `urn:air:<host>:knowledge:<bundle.id>` for the discovery document and `urn:air:<host>:a2a:<bundle.id>` for the card, `<host>` being the host name of `site.base` in lower case and without a port, which for this switch MUST be a fully qualified domain name (it contains at least one `.`, is not an IP literal and does not end in `.local`; the form is that of ARD §4.2, `urn:air:<publisher>:[<namespace>:]<agent-name>`); `displayName`, `site.title`; `type`, for the discovery document the media type that AGSC-06-17 serves it with, parameter included (`application/linkset+json; profile="https://w3id.org/agentic-system-core/profile/agentic-knowledge"`), and for the card `application/a2a-agent-card+json`; `url`, the absolute URL of the file; `description`, the Bundle description when there is one; and the SHA-256 of the exact bytes served at `url`, written `sha256:` and 64 lowercase hexadecimal characters, as the member `digest` in `ai-catalog.json` (the AI Catalog draft's form) and as the member `metadata.digest` in `ard.json`, which defines no digest member on an entry. A writer MUST NOT write `representativeQueries`, which ARD asks of an entry and which would have to be invented; a validator of ARD reports their absence as a warning, and this rule accepts it. The link relations `ard` and `ai-catalog` are not emitted, because AGSC-06-35 admits registered relation names only. A reader of this specification never needs either file. A switch set on a node whose `site.base` host is not a fully qualified domain name is rejected at build and reported as `AGSC-E209`, and a switch set on a node with no `bundle.id` is rejected as `AGSC-E202`; in both no file is written. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: catalogue crawlers look for these two well-known names; one entry that points at the discovery document, with its digest, lets them find the node without a second format of our own)* [design, ARD v0.91, AI Catalog draft]
- **AGSC-06-46** **The link relations of llms.txt v2 on generated pages.** Every generated HTML page MUST carry in its `<head>` `<link rel="describedby" type="text/plain" href="/llms.txt">`, and every item page MUST also carry `<link rel="alternate" type="text/markdown" href="/pages/<slug>.md">`: the two relations that llms.txt v2 (modified 2026-08-10, llmstxt.org, read 2026-10-29) defines for a page, `describedby` for the llms.txt file that covers it and `alternate` with the type `text/markdown` for the Markdown version of the page. A page may carry several `describedby` links, and a reader selects the discovery document by its type (AGSC-06-25). `/llms.txt` and `/llms-full.txt` are not changed by this rule. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: llms.txt v2 defines page-level relations as well as the file; 1.0 pages linked the Markdown copy (AGSC-06-02) without saying which relation it was)* [design, llms.txt v2]
