# AGSC-10 — Implementation profiles (conformance Levels 0–3)

Purpose: let any language, framework or existing software implement a compatible Agentic Knowledge Web node from these files alone. [PRD-055]

## 10.1 Levels
- **AGSC-10-01** A conformance claim MUST name exactly one Level — the Level *is* the class of AGSC-00-09…12 and AGSC-09-01 (publisher = 0, reader = 1, writer = 2, full engine = 3), so there is one claim vocabulary, not two — and MUST be backed by a green run of **the Level's vector set** (AGSC-09-04, areas listed below). A claim MUST NOT be conditioned on any particular validator program: the shipped `tools/` of AGSC-09-90 are one implementation of the nine command contracts, and a claimant names which implementation it ran (AGSC-09-90), but the vectors — not a program — are what a claim asserts. An area listed for a Level that has no vector file on disk contributes nothing to the claim (AGSC-09-90); the claim states the areas *and* the vector count actually run. [PRD-055, PRD-054]
- **AGSC-10-02** **Level 0 — Publisher.** Static files only, producible by any CMS/wiki export. A Level-0 node serves these routes at its origin: `/.well-known/knowledge-linkset` (AGSC-06-08..12), `/graph.jsonld` (AGSC-05, JSON-LD view only) and `/llms.txt` (AGSC-06-13…15). They are produced from a Bundle: items as `content/<type-plural>/<slug>.md` with the required frontmatter (AGSC-02; `prov` is required at every Level, and an item without it is `AGSC-E501` under AGSC-08-01 — the required case `fm-0004` sits in the `frontmatter` area, which Level 0 runs), and the root document `content/index.md` (AGSC-01-04). These files are what the `frontmatter`, `slug` and `bundle` cases read; they are the node's source and not routes, and a Level-0 node is not asked to serve them, an item page or a per-item copy, which are routes of the Level-2 set (AGSC-06-01, AGSC-10-04). The well-known file at this Level takes the Level-0 form of AGSC-06-08a: a CMS export has no ledger and no `graph.nq`, and Level 0 does not ask for one. The discovery link of AGSC-06-25 SHOULD also be emitted. Vector areas: `frontmatter`, `slug`, `bundle`, `discovery` (the Level-0 case is `disc-0004`; `jcs` enters at Level 1, since Level-0 JSON need only be I-JSON). Level 0 requires valid I-JSON, not canonical bytes — AGSC-04-04's Level-0 carve-out. No engine, no build tool required. *(Amended 2026-10-07 for 1.0.0: until `1.0.0-rc.7` this rule said that a Level-0 item without a provenance block inherits `prov.operator` from `bundle.operator` with the warning `AGSC-E508`; AGSC-08-01, the required case `fm-0004` and the reference engine all report `AGSC-E501`, and no implementation performed the inheritance. The rule now states what the case has always checked; `AGSC-E508` stays registered and is raised by no 1.0 rule. Whether a later version lets a Level-0 export inherit provenance is a question for 1.1 (AGSC-00-20).)* *(Amended 2026-10-10 for 1.0.0: the rule listed the Bundle's files among what a Level-0 node serves; it now names the routes the node serves and says that the content files are the Bundle the Level-0 cases read.)* *(Amended 2026-10-29 for 1.1.0: settled for 1.1: provenance stays required at every Level and no `prov.operator` is inherited from `bundle.operator`; the question the 1.0 note left open is closed)* [PRD-055]
- **AGSC-10-03** **Level 1 — Reader.** Level 0 + parsing/validation of any conforming Bundle: frontmatter contract, slug grammar, fourteen Links (nine core + five Mode-2) with computed inverses, orphan/cycle detection, error codes. Vector areas: + `links`, `lint`, `jcs`. [PRD-055, PRD-002, PRD-003]
- **AGSC-10-04** **Level 2 — Writer/Exporter.** Level 1 + deterministic emission of all surfaces (AGSC-04 canonicalization, AGSC-05 four RDF views, AGSC-06 route set incl. search/NOW/ledger and the discovery link of AGSC-06-25) and export/import (AGSC-01-22…29: Markdown/OKF/JSON-LD/JSONL/steer/skills; the SKOS adapter of AGSC-01-39 is an adapter and is not required below Level 3, AGSC-10-19). Level 2 is therefore the writer of AGSC-00-10 **plus** AGSC-01-22…29 (interchange) and AGSC-08-20…24 (the derived ledger, which the route set publishes): a public node claiming Level 2 MUST publish `/ledger.jsonl` and link it with the `…/rel#ledger` link of AGSC-06-08, which is why a build given no git-log file cannot support the claim (AGSC-06-01); everything else in §08 — provenance gates, trailers, the four lints, channels — is Level 3. Vector areas: + `graph`, `build`, `adopt`, `ledger`, `import`, `export`, `skills`, `chunks`, `boards`, `boundary`. [PRD-055, PRD-022]
- **AGSC-10-05** **Level 3 — Full engine.** Level 2 + composition (AGSC-07), governance (AGSC-08), CLI contract and MCP tools (AGSC-09-13). Vector areas: all. A claim of Level 3, like a claim of any Level, exists only after a green run of that Level's set (AGSC-10-01, AGSC-10-15); the reference implementation (`agentic-system-core`) publishes its own claim in the form of AGSC-09-01. *(Amended 2026-10-02 for 1.0.0: until `1.0.0-rc.6` this rule said that the reference implementation "will claim Level 3 at its 1.0.0 release"; a rule states no future event.)* [PRD-055, PRD-001]
- **AGSC-10-06** A higher Level MUST include every rule of the lower Levels; a claim MUST NOT cherry-pick rules within a Level. [PRD-055]

> *Where a node can live (informative).* A Bundle is a file set and a build is a file set; neither depends on a transport. A node may therefore be deployed on any substrate — a web host, a local machine, a git repository, a content-addressed network, a device, or a ledger-anchored store — through a deployment profile (the plugin kind of §0.6, AGSC-00-24). Conformance at any Level is claimed for an origin: the discovery document and the routes of §6 are served over HTTPS at that origin, by the substrate itself or by a web interface in front of it, and a ledger may anchor the bundle hash and the content version (AGSC-06-08, AGSC-04-25) as a record of its own. The Cloudflare Pages profile is the reference; other profiles are implementation-defined at 1.x. No obligation changes here, and a 1.0 reader may ignore this paragraph.

## 10.2 Foreign knowledge bases
- **AGSC-10-07** A platform exposing its own knowledge base as a node MAY keep its native storage; it MUST present the Level-0 files at the documented URLs (generated at publish time is sufficient) and MUST map its native identifiers to slugs (AGSC-01-10) and its native links to the fourteen keys (AGSC-03-19 import synonyms) — unmapped native relations become `related`. [PRD-055]
- **AGSC-10-08** `memory://<bundle-id>/<slug>` is the platform-neutral alias of an item's HTTPS IRI (AGSC-05-01); a foreign node MUST declare its `bundle-id` as `bundle.id` of its configuration (AGSC-01-18), and MAY resolve the alias internally to its native record *(Rationale: the schema of `content/index.md` carries no key for the id, so the configuration is where it is declared.)*. The configuration is a file of the Bundle, not a route: declaring the id there is what this rule asks. No route of AGSC-06-01 is required to carry it — the page tools of AGSC-09-16 hold it in their script, so that a page resolves the alias as the local tool server does — and another node addresses a foreign node's items by their HTTPS IRIs (AGSC-05-04b refuses a foreign `bundle-id` with `AGSC-E309`). *(Amended 2026-10-02 for 1.0.0: the sentence "and SHOULD state it in `content/index.md`" is removed — that file's schema has no key for it, so no node could follow it.)* AGSC-05-04a governs the equivalence of the two forms; a node that never emits or accepts `memory://` still conforms. *(Amended 2026-10-10 for 1.0.0: "publish" read as if a route served the id; the configuration is not a route, so the rule says "declare" and names what carries the id.)* [PRD-027]
- **AGSC-10-09** Exporting from a foreign node to a package (Markdown/OKF bundle, Skill packs, JSON-LD) MUST follow AGSC-01-26..29 so that the reference engine (or any Level-1 reader) imports it losslessly; the Content Use Terms embedding rule applies only to prose licensed under those terms — foreign nodes declare their own `license` per item. [PRD-055]

## 10.4 Federation — mutual conformance
- **AGSC-10-12** Two nodes federate by each listing the other in its well-known linkset with relation `peer` (`…/rel#peer`, defined in AGSC-06-10). `tools/validate-wellknown --peer <url|file>` (AGSC-09-93) MUST verify, for both nodes: the link set resolves, every `digest` and every REQUIRED `agsc-*` target attribute validates (Levels ≥2, AGSC-06-08/08a), and each node's `peer` entry names the other's canonical well-known URL. No separate federation validator exists — `--peer` is the whole check, and it MUST accept two local files so the check runs with no network. This mutual check is the Agentic Knowledge Web's smallest protocol; a directory service is a v2 backend component. Vector `disc-0005`. [PRD-024]

> **Pointer:** the federation protocol is specified in full in `spec/11-boundary.md` §11.3 (F1, F2, F4–F9); AGSC-10-12 remains the mutual check it names. A tombstoned peer (AGSC-11-23) is *resolved, not mutual*.


## 10.5 Project mode — items as tasks, clusters as boards

- **AGSC-10-13** A Bundle is readable as a project board without a new data model: every `concept` of `kind: task` is a task whose state is `task_state` (AGSC-02-99), every cluster containing at least one task is a board, and the fourteen Links keep their meaning (`blocked-by` is the dependency edge, `decided-by` the decision link). A Level ≥ 2 writer MUST emit `/boards/index.json` `{boards: [{cluster, iri, tasks}]}` and `/boards/<cluster-slug>.json` `{board, done, generated_at, iri, tasks: [{slug, iri, title, state, status, blocked_by, decided_by, modified, claimed_by?}]}` — JCS-canonical, tasks sorted by slug, `state` the verbatim A2A value, the board object carries the derived boolean `done` (true when every task's state is terminal: `TASK_STATE_COMPLETED`, `TASK_STATE_CANCELED`, `TASK_STATE_REJECTED` or `TASK_STATE_FAILED`; a board with no task is never emitted) and each task an OPTIONAL `claimed_by` (the `author` of the last first-parent commit whose `files[]` names the task's file, derived at build from the extended git-log file of AGSC-08-20b — never authored, absent when no history exists or when the file carries no `files[]` or `author` *(Rationale: that file records which files a commit touched and not which keys changed, so the last change of `task_state` itself cannot be derived from it.)*), `blocked_by`/`decided_by` arrays of **slugs local to the board's own Bundle**, which a merging client expands to item IRIs as AGSC-05-01 forms them — the origin of the board's `iri`, the type folder of the item the slug names, and the slug, with a trailing slash; a slug that names a task of the same board expands to that task's `iri`, and the type folder of a Concept is `concepts/` (AGSC-11-15) — whenever at least one task exists, and MUST emit nothing under `/boards/` otherwise. The route is added to AGSC-06-01. A writer that emits `/boards/index.json` MUST link it from the discovery document as `https://w3id.org/agentic-system-core/rel#boards` with `type` `application/json` and, at Level ≥ 2, `digest` (AGSC-06-08, AGSC-06-10) *(Rationale: without this relation no link of the closed set points at the board, and a live board is not discoverable from the discovery document.)*. *(Amended 2026-10-10 for 1.0.0: the expansion of a board slug named only the origin, and an item IRI also holds the type folder.)* [PRD-057]
- **AGSC-10-14** Serving a board **live** — an Agent2Agent server answering task operations — is version-2 scope and is declared, when present, as a `responder` surface whose `agsc-surface-version` is `a2a:<version>` (AGSC-11-21). A client merging boards across nodes follows AGSC-11-15. [design]

- **AGSC-10-15** **The Level is the single source of the vector set.** AGSC-10-02…05 name the required vector areas for Levels 0–3; the class sentences of AGSC-00-09…11 describe what each class *implements* and MUST NOT be read as a second, competing list of areas. Where the two ever differ, this rule settles it: a claim runs the areas of AGSC-10-02…05 for its Level and nothing else. From 1.1 a claim lists a Level's areas in **one fixed order**: the order in which AGSC-09-04 names the twenty-five areas — `frontmatter`, `slug`, `links`, `jcs`, `graph`, `lint`, `cli`, `bundle`, `prov`, `ledger`, `compose`, `build`, `discovery`, `adopt`, `import`, `export`, `skills`, `adapters`, `channels`, `harness`, `run`, `conform`, `boundary`, `chunks`, `boards` — restricted to the areas the Level names, and a claim's list is compared as a sequence. ## 10.6 Mode 5 — the live board: a self-driving working memory for product and project management

- **AGSC-10-16** A **live board** is a Bundle that (a) holds at least one board (AGSC-10-13 — tasks of `kind: task` with `task_state`, clusters as boards) beside the project's decisions, specs, gates, procedures, episodes and lessons (Modes 2 and 3); (b) declares where proposals go (`contribute[]`, AGSC-11-14) and at least one participation surface — `mcp`, `webmcp`, a `responder` (AGSC-11-16, AGSC-11-21) or a channel (AGSC-01-30); and (c) MAY run one or more agent lanes (AGSC-08-28) whose `tasks[]` include `plan`, `claim` and `work`. It is a pull system — a task is pulled by whoever claims it, at most `max_claims` at a time (AGSC-10-17), and flows through its states until the board is done — and, in its architecture, the blackboard pattern realised on this format: the Bundle is the shared data structure every participant — a person, a local agent, a remote agent — reads through the published surfaces and writes to only through Proposals; the control is the sequence of gates, reviews and the standing ratification of AGSC-08-29; the knowledge sources are the agent lanes, the channels and the people. No type, key or ontology term is added. [PRD-064]
- **AGSC-10-17** **Claim and progress.** On a live board a change of a task's `task_state` is a Proposal whose diff touches that key, `modified` and nothing else of the task; a participant claims a task by proposing `TASK_STATE_WORKING` under its own `prov.agent`/`prov.operator`; concurrent claims resolve by forge merge order, the later one being a conflict its author re-proposes against the merged state; an agent lane MUST NOT hold more than its `max_claims` tasks in `TASK_STATE_WORKING` at once (AGSC-01-36, default one — the work-in-progress limit that makes the board a pull system), a claim beyond it being rejected with `AGSC-E511` before any lint runs; a claimed task whose `stale_after` has passed is reported stale by `refresh` like any item (AGSC-02-11, the comparison against the build instant). The board export carries the derived `claimed_by` and `done` of AGSC-10-13 so that a reader sees who holds a task, and whether the board is finished, without reading git; the holder of a task is its derived `claimed_by` and, where that is absent, the task's `prov.agent`, and every count of held tasks — `max_claims` above and the work-in-progress limit — reads the holder this way, a claim of a task already held in `TASK_STATE_WORKING` by another participant being `AGSC-E511`. An agent lane whose `tasks[]` include `work` runs, on its schedule, while the boards it may touch hold a task it can claim — `TASK_STATE_SUBMITTED`, or `TASK_STATE_WORKING` under its own name — and stops when every such board is `done`, when a task needs a person (`TASK_STATE_INPUT_REQUIRED`, `TASK_STATE_AUTH_REQUIRED` — both are slow-lane states), or when its budget is reached (AGSC-08-28(e)); "until done" is therefore a property of the board, not of the agent. The refusal applies to every caller of `propose`, a declared lane or not; a task in `TASK_STATE_WORKING` whose holder cannot be derived is held by another participant for every caller; and an author `process:<name>` (AGSC-08-20b) and the agent lane `<name>` are the same participant. [AGSC-02-99]
- **AGSC-10-18** **Two lanes.** A live board has a **fast lane** — everything that runs without a fresh human decision: agent lanes, `auto` channel merges, `refresh`, the derived ledger, the board export, the mutual peer check — and a **slow lane** — everything that requires one: gates (AGSC-08-09), human review (AGSC-08-03), decisions (Concepts of `kind: decision`), releases, retirement, and every change to a procedure, gate, cluster, configuration, workflow or schema. A conforming live board MUST keep the slow-lane set unreachable from the fast lane (AGSC-08-26(b), AGSC-08-28(c)) and MUST make the fast lane auditable through the ledger's `mode: "auto"` entries and the Episode of every run (AGSC-08-28(d)). Remote participation follows §11: the live board is pulled, never pushed — nodes never call nodes (AGSC-11-06…11) — and a remote participant proposes through a `contribute[]` target, a channel or a declared responder (AGSC-11-14, AGSC-11-21), so that a live board shared by many agents and people needs no server of its own. [PRD-064, ADR-014]

## 10.7 The Levels of the additions of 1.1

- **AGSC-10-19** **Where an addition of 1.1 sits.** An addition of 1.1 belongs to the Level of the area whose cases pin it, and no claim of a lower Level runs it (AGSC-10-15). A reader of Level 1 tolerates a newer MINOR in a discovery document (`disc-0023`) and checks the configuration keys of AGSC-01-18, the portable-name warnings of AGSC-01-40, the nesting bound of AGSC-02-02, the domain keys of AGSC-02-25, the minimum-sources check of AGSC-08-31 and the context rule of AGSC-08-32. A writer of Level 2 sends the Signposting links, the Dataset fields, the catalogue files, the agent card and the chunk-integrity attributes (AGSC-06-34, AGSC-06-40 to AGSC-06-44; `disc-0026` to `disc-0033`) and applies the draft rule of AGSC-01-22, the builder-independent ledger entry and the author map of AGSC-08-20a, the restricted-node rules of AGSC-11-20 and the fail-closed fetch of AGSC-11-08. The SKOS adapter of AGSC-01-39, the context maps of AGSC-11-24, the suggestions of AGSC-05-35, the check of AGSC-09-20 and the tool hints of `bnd-0050` belong to the full engine of Level 3, because the first is an optional adapter (AGSC-01-26a), the second is the behaviour of a federating client and the others are verbs and tools of the CLI contract (AGSC-10-05). The diagram grammar of AGSC-01-42 binds a writer that compiles `.diagram` files, and its cases `bundle-0018` and `bundle-0019` are Level 3: a Level 2 writer that does not compile them emits no SVG for them and is not asked to pass a case that needs one. A node that does not use the domain layer (AGSC-01-41) is unaffected at every Level. *(Amended 2026-10-29 for 1.1.0: rule added for 1.1.0: the Level of each addition of 1.1)* [PRD-055, AGSC-10-01, AGSC-10-15]
