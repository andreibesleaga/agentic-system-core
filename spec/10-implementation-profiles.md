# AGSC-10 — Implementation profiles (conformance Levels 0–3)

Purpose: let any language, framework or existing software implement a compatible Agentic Knowledge Web node from these files alone. [PRD-055]

## 10.1 Levels
- **AGSC-10-01** A conformance claim MUST name exactly one Level — the Level *is* the class of AGSC-00-09…12 and AGSC-09-01 (publisher = 0, reader = 1, writer = 2, full engine = 3), so there is one claim vocabulary, not two — and MUST be backed by a green run of **the Level's vector set** (AGSC-09-04, areas listed below). A claim MUST NOT be conditioned on any particular validator program: the shipped `tools/` of AGSC-09-90 are one implementation of the nine command contracts, and a claimant names which implementation it ran (AGSC-09-90), but the vectors — not a program — are what a claim asserts. *(Amended at rc.3: the previous text made a claim impossible until the reference validators existed, which was a publication blocker.)*. An area listed for a Level that has no vector file on disk contributes nothing to the claim (AGSC-09-90); the claim states the areas *and* the vector count actually run. [PRD-055, PRD-054]
- **AGSC-10-02** **Level 0 — Publisher.** Static files only, producible by any CMS/wiki export: `content/<type-plural>/<slug>.md` items with the required frontmatter (AGSC-02; at this Level an item without `prov` inherits `prov.operator` from `bundle.operator` with `prov.origin: imported`, reported as the warning `AGSC-E508`, so that an export closes at Level 0 without an engine), `content/index.md` (AGSC-01-04), `/.well-known/knowledge-linkset` (AGSC-06-08..12), `/graph.jsonld` (AGSC-05, JSON-LD view only) and `/llms.txt` (AGSC-06-13…15). The well-known file at this Level takes the Level-0 form of AGSC-06-08a: a CMS export has no ledger and no `graph.nq`, and Level 0 does not ask for one. The discovery link of AGSC-06-25 SHOULD also be emitted. Vector areas: `frontmatter`, `slug`, `bundle`, `discovery` (the Level-0 case is `disc-0004`; `jcs` enters at Level 1, since Level-0 JSON need only be I-JSON). Level 0 requires valid I-JSON, not canonical bytes — AGSC-04-04's Level-0 carve-out. No engine, no build tool required. [PRD-055]
- **AGSC-10-03** **Level 1 — Reader.** Level 0 + parsing/validation of any conforming Bundle: frontmatter contract, slug grammar, fourteen Links (nine core + five Mode-2) with computed inverses, orphan/cycle detection, error codes. Vector areas: + `links`, `lint`, `jcs`. [PRD-055, PRD-002, PRD-003]
- **AGSC-10-04** **Level 2 — Writer/Exporter.** Level 1 + deterministic emission of all surfaces (AGSC-04 canonicalization, AGSC-05 four RDF views, AGSC-06 route set incl. search/NOW/ledger and the discovery link of AGSC-06-25) and export/import (AGSC-01-22…29: Markdown/OKF/JSON-LD/JSONL/steer/skills). Level 2 is therefore the writer of AGSC-00-10 **plus** AGSC-01-22…29 (interchange) and AGSC-08-20…24 (the derived ledger, which the route set publishes): a public node claiming Level 2 MUST publish `/ledger.jsonl` and link it with the `…/rel#ledger` link of AGSC-06-08, which is why a build given no git-log file cannot support the claim (AGSC-06-01) *(stated at rc.6, 2026-09-24: both public reference nodes had passed a Level-2 check with no ledger at all, because the checker tested the ledger head only when the link was present)*; everything else in §08 — provenance gates, trailers, the four lints, channels — is Level 3. Vector areas: + `graph`, `build`, `adopt`, `ledger`, `import`, `export`, `skills`, and (rc.3) `chunks`, `boards`, `boundary`. [PRD-055, PRD-022]
- **AGSC-10-05** **Level 3 — Full engine.** Level 2 + composition (AGSC-07), governance (AGSC-08), CLI contract and MCP tools (AGSC-09-13). Vector areas: all. The reference implementation (`agentic-system-core`) will claim Level 3 at its 1.0.0 release; no claim exists before a green run of the Level-3 set. [PRD-055, PRD-001]
- **AGSC-10-06** A higher Level MUST include every rule of the lower Levels; a claim MUST NOT cherry-pick rules within a Level. [PRD-055]

> *Where a node can live (informative, added at rc.6, 2026-09-24).* A Bundle is a file set and a build is a file set; neither depends on a transport. A node may therefore be deployed on any substrate — a web host, a local machine, a git repository, a content-addressed network, a device, or a ledger-anchored store — through a deployment profile (the plugin kind of §0.6, AGSC-00-24). Conformance at any Level is claimed for an origin: the discovery document and the routes of §6 are served over HTTPS at that origin, by the substrate itself or by a web interface in front of it, and a ledger may anchor the bundle hash and the content version (AGSC-06-08, AGSC-04-25) as a record of its own. The Cloudflare Pages profile is the reference; other profiles are implementation-defined at 1.x. No obligation changes here, and a 1.0 reader may ignore this paragraph.

## 10.2 Foreign knowledge bases
- **AGSC-10-07** A platform exposing its own knowledge base as a node MAY keep its native storage; it MUST present the Level-0 files at the documented URLs (generated at publish time is sufficient) and MUST map its native identifiers to slugs (AGSC-01-10) and its native links to the fourteen keys (AGSC-03-19 import synonyms) — unmapped native relations become `related`. [PRD-055]
- **AGSC-10-08** `memory://<bundle-id>/<slug>` is the platform-neutral alias of an item's HTTPS IRI (AGSC-05-01); a foreign node MUST publish its `bundle-id` as `bundle.id` of its configuration (AGSC-01-18) and SHOULD state it in `content/index.md`, and MAY resolve the alias internally to its native record *(amended 2026-09-24: the rule required the id in `content/index.md`, a document whose schema carries no such key, so no node could comply)*. AGSC-05-04a governs the equivalence of the two forms; a node that never emits or accepts `memory://` still conforms. [PRD-027]
- **AGSC-10-09** Exporting from a foreign node to a package (Markdown/OKF bundle, Skill packs, JSON-LD) MUST follow AGSC-01-26..29 so that the reference engine (or any Level-1 reader) imports it losslessly; the Content Use Terms embedding rule applies only to prose licensed under those terms — foreign nodes declare their own `license` per item. [PRD-055]

## 10.3 Guide and mapping
- **AGSC-10-10** The 1.0.0 distribution MUST include `docs/IMPLEMENTERS-GUIDE.md` (authored in October 2026): a ≤10-step path to a Level-0 node in any stack, the per-Level rule/vector checklist, and a platform mapping table (at minimum: MediaWiki, WordPress, Docusaurus/MkDocs/Hugo, Notion/Confluence export, Obsidian/Logseq, generic Django/Laravel/Rails app) mapping their constructs to items, frontmatter keys, Links and Clusters. [PRD-055]
- **AGSC-10-11** The guide MUST be verifiable: every step names the validator that proves it, and the reference distribution's own end-to-end run MUST include one Level-0 node produced without the reference engine. The reference `tools/` validators (Node ≥22.14 in the reference implementation) are a **convenience, not a requirement**: a conformance claim MAY instead be backed by the claimant's own run of `tests/vectors/**` in any language, reported per AGSC-09-02 and AGSC-09-03. `docs/IMPLEMENTERS-GUIDE.md` MUST state both routes and MUST NOT present Node as a prerequisite for any Level — PRD-055's "validated without our engine" is satisfied by either. [PRD-055, PRD-054]

## 10.4 Federation — mutual conformance (added 2026-09-03)
- **AGSC-10-12** Two nodes federate by each listing the other in its well-known linkset with relation `peer` (`…/rel#peer`, defined in AGSC-06-10). `tools/validate-wellknown --peer <url|file>` (AGSC-09-93) MUST verify, for both nodes: the link set resolves, every `digest` and every REQUIRED `agsc-*` target attribute validates (Levels ≥2, AGSC-06-08/08a), and each node's `peer` entry names the other's canonical well-known URL. No separate federation validator exists — `--peer` is the whole check, and it MUST accept two local files so the check runs with no network. This mutual check is the Agentic Knowledge Web's smallest protocol; a directory service is a v2 backend component. Vector `disc-0005`. [PRD-024]

> **rc.3 pointer (2026-09-16; corrected at rc.5):** the federation protocol is specified in full in `spec/11-boundary.md` §11.3 (F1, F2, F4–F9); AGSC-10-12 remains the mutual check it names. A tombstoned peer (AGSC-11-23) is *resolved, not mutual*.


## 10.5 Project mode — items as tasks, clusters as boards (added at rc.3, 2026-09-16)

- **AGSC-10-13** A Bundle is readable as a project board without a new data model: every `concept` of `kind: task` is a task whose state is `task_state` (AGSC-02-99), every cluster containing at least one task is a board, and the fourteen Links keep their meaning (`blocked-by` is the dependency edge, `decided-by` the decision link). A Level ≥ 2 writer MUST emit `/boards/index.json` `{boards: [{cluster, iri, tasks}]}` and `/boards/<cluster-slug>.json` `{board, done, generated_at, iri, tasks: [{slug, iri, title, state, status, blocked_by, decided_by, modified, claimed_by?}]}` (`done` and `claimed_by` added to these member lists at rc.5: the rule required both below and the lists omitted them) — JCS-canonical, tasks sorted by slug, `state` the verbatim A2A value, at rc.4 the board object carries the derived boolean `done` (true when every task's state is terminal: `TASK_STATE_COMPLETED`, `TASK_STATE_CANCELED`, `TASK_STATE_REJECTED` or `TASK_STATE_FAILED`; a board with no task is never emitted) and each task an OPTIONAL `claimed_by` (the `author` of the last first-parent commit whose `files[]` names the task's file, derived at build from the extended git-log file of AGSC-08-20b — never authored, absent when no history exists or when the file carries no `files[]` or `author` *(derivation restated 2026-09-24: it read "the `prov.agent`, else `prov.operator`, of the last merged change of `task_state`", which no writer can derive from that file, since it records which files a commit touched and not which keys changed)*), `blocked_by`/`decided_by` arrays of **slugs local to the board's own Bundle**, which a merging client expands to IRIs by prefixing the board's `iri` origin (AGSC-11-15) — whenever at least one task exists, and MUST emit nothing under `/boards/` otherwise. The route is added to AGSC-06-01. [PRD-057]
- **AGSC-10-14** Serving a board **live** — an Agent2Agent server answering task operations — is version-2 scope and is declared, when present, as a `responder` surface whose `agsc-surface-version` is `a2a:<version>` (AGSC-11-21). A client merging boards across nodes follows AGSC-11-15. [design]

- **AGSC-10-15** (added at rc.3) **The Level is the single source of the vector set.** AGSC-10-02…05 name the required vector areas for Levels 0–3; the class sentences of AGSC-00-09…11 describe what each class *implements* and MUST NOT be read as a second, competing list of areas. Where the two ever differed, this rule settles it: a claim runs the areas of AGSC-10-02…05 for its Level and nothing else. This rule fixes **no order** for a Level's area set: the set is what the Level names, a claim's area list is compared **set-wise**, and an order is a 1.1 addition if one is ever wanted (stated at rc.5, so that `conform-0003`'s set-wise comparison is the rule rather than an accepted reading). *(Amended at rc.3: the earlier wording asserted an identity between class and Level while listing different areas in the two places — the class-versus-level defect.)* [AGSC-00-12, AGSC-09-01]

## 10.6 Mode 5 — the live board: a self-driving working memory for product and project management (added at rc.4, 2026-09-17; named *Blackboard*, then *Kanban*, then **live board** on 2026-09-18)

- **AGSC-10-16** A **live board** is a Bundle that (a) holds at least one board (AGSC-10-13 — tasks of `kind: task` with `task_state`, clusters as boards) beside the project's decisions, specs, gates, procedures, episodes and lessons (Modes 2 and 3); (b) declares where proposals go (`contribute[]`, AGSC-11-14) and at least one participation surface — `mcp`, `webmcp`, a `responder` (AGSC-11-16, AGSC-11-21) or a channel (AGSC-01-30); and (c) MAY run one or more agent lanes (AGSC-08-28) whose `tasks[]` include `plan`, `claim` and `work`. It is a pull system — a task is pulled by whoever claims it, at most `max_claims` at a time (AGSC-10-17), and flows through its states until the board is done — and, in its architecture, the blackboard pattern realised on this format: the Bundle is the shared data structure every participant — a person, a local agent, a remote agent — reads through the published surfaces and writes to only through Proposals; the control is the sequence of gates, reviews and the standing ratification of AGSC-08-29; the knowledge sources are the agent lanes, the channels and the people. No type, key or ontology term is added. [PRD-064]
- **AGSC-10-17** **Claim and progress.** On a live board a change of a task's `task_state` is a Proposal whose diff touches that key, `modified` and nothing else of the task; a participant claims a task by proposing `TASK_STATE_WORKING` under its own `prov.agent`/`prov.operator`; concurrent claims resolve by forge merge order, the later one being a conflict its author re-proposes against the merged state; an agent lane MUST NOT hold more than its `max_claims` tasks in `TASK_STATE_WORKING` at once (AGSC-01-36, default one — the work-in-progress limit that makes the board a pull system), a claim beyond it being rejected with `AGSC-E511` before any lint runs; a claimed task whose `stale_after` has passed is reported stale by `refresh` like any item (AGSC-02-11, the comparison against the build instant — corrected at rc.5: the earlier citation, AGSC-02-06, fixes the instant *format*, not staleness). The board export carries the derived `claimed_by` and `done` of AGSC-10-13 so that a reader sees who holds a task, and whether the board is finished, without reading git; the holder of a task is its derived `claimed_by` and, where that is absent, the task's `prov.agent`, and every count of held tasks — `max_claims` above and the work-in-progress limit — reads the holder this way, a claim of a task already held in `TASK_STATE_WORKING` by another participant being `AGSC-E511` *(stated at rc.6, 2026-09-24: two readings of who holds a task coexisted)*. An agent lane whose `tasks[]` include `work` runs, on its schedule, while the boards it may touch hold a task it can claim — `TASK_STATE_SUBMITTED`, or `TASK_STATE_WORKING` under its own name — and stops when every such board is `done`, when a task needs a person (`TASK_STATE_INPUT_REQUIRED`, `TASK_STATE_AUTH_REQUIRED` — both are slow-lane states), or when its budget is reached (AGSC-08-28(e)); "until done" is therefore a property of the board, not of the agent. [AGSC-02-99]
- **AGSC-10-18** **Two lanes.** A live board has a **fast lane** — everything that runs without a fresh human decision: agent lanes, `auto` channel merges, `refresh`, the derived ledger, the board export, the mutual peer check — and a **slow lane** — everything that requires one: gates (AGSC-08-09), human review (AGSC-08-03), decisions (Concepts of `kind: decision`), releases, retirement, and every change to a procedure, gate, cluster, configuration, workflow or schema. A conforming live board MUST keep the slow-lane set unreachable from the fast lane (AGSC-08-26(b), AGSC-08-28(c)) and MUST make the fast lane auditable through the ledger's `mode: "auto"` entries and the Episode of every run (AGSC-08-28(d)). Remote participation follows §11: the live board is pulled, never pushed — nodes never call nodes (AGSC-11-06…11) — and a remote participant proposes through a `contribute[]` target, a channel or a declared responder (AGSC-11-14, AGSC-11-21), so that a live board shared by many agents and people needs no server of its own. [PRD-064, ADR-014]
