# Testing

**Who this is for:** a developer or a contributor running or adding tests. **Read after:** [CODE-ORIENTATION.md](CODE-ORIENTATION.md).

## Summary

Every level of this distribution is tested, from one function to the whole command line on real Bundles, and every rule of the specification is accounted for. `npm test` runs the unit, integration and architecture tests, the conformance vectors, the executed acceptance scenarios, the tests of the standard itself and the end-to-end tests that need nothing outside this repository. Two further end-to-end lanes — the real Bundles and a real browser — are optional because they need files or a program the repository does not carry; each says why when it is skipped.

A generated matrix, [`docs/RULE-COVERAGE.md`](RULE-COVERAGE.md), lists for every active rule the checks that verify it. The suite fails when a rule has no check and no stated reason, and when that page is out of date. Rules the reference engine does not implement yet are listed there as gaps, with what is missing, and are never counted as verified.

## The levels

| Level | Where | What it proves | How to run it |
|---|---|---|---|
| Unit | `tests/<context>/` (`knowledge`, `governance`, `distribution`, `composition`, `interchange`, `boundary`, `adapters`, `ports`) | one module does what the rules it cites say, for the cases its title names; `tests/security/` is the seeded fuzz lane of the text scanners (each returns what the pattern it replaced returned, in a constant number of steps per character) | `npm test`, or `node --test "tests/knowledge/*.test.js"` |
| Integration | `tests/application/`, `tests/bin/`, `tests/connectors/` | the command line, spawned as a user runs it, wires the modules together; exit codes and envelopes | `npm test` |
| Architecture | `tests/arch/` | the context boundaries, the pinned libraries, the package's file list, the plugin contract | `npm test`; the slower audit lane with `AGSC_AUDIT=1 node --test tests/arch/*.test.js` (the switch belongs to the architecture lane; the tests that start the command keep every `AGSC_` name away from it, so the whole suite passes with it set too) |
| Conformance vectors | `tests/vectors/`, run by `tests/conformance/vector-runner.test.js` | every required vector passes; withdrawn vectors are skipped and counted | `npm test`, or `agsc conform --level <n>` |
| Acceptance | `features/*.feature`, run by `tests/acceptance/features.test.js` with the steps of `tests/acceptance/steps/` | the persona scenarios, executed against the real command line and the real local tool server on a copy of `tests/acceptance/bundle/` | `npm run test:acceptance` |
| The standard itself | `tests/standard/` | the specification, schemas, vectors, route set, discovery relations and Internet-Draft agree with one another; the rules no vector pins; the rule-coverage matrix | `npm run test:standard` |
| End to end | `tests/e2e/`, `tests/e2e/modes/` | a Level-0 node written without the engine passes the shipped checker; each of the six modes walked from an empty folder, as a person and as an agent would (one file per mode under `tests/e2e/modes/`); with the options below, the two real Bundles through every verb, and the page tools in a browser | `npm run test:e2e` |
| Guides and demos | `tests/docs/` | every runnable block of `docs/DEMOS.md` and of the seven guides of `docs/guides/` (the six mode guides and the publishing guide) runs in a scratch copy and prints what the page says it prints; the agent skill is well formed and its copy in the plugin equals it; the governance texts agree with each other and with the coverage thresholds of `test:coverage` | `npm test`, or `node --test tests/docs/demos.test.js tests/docs/guides.test.js tests/docs/agent-skill.test.js` |
| Checkers | `tests/tools/` | each shipped checker and generator on good and bad input, with no import from `src/` | `npm test` |
| Benchmark kit | `tests/bench/` | the benchmark kit (`bench/`, `tools/bench`) and its measurement script | `npm test`, or `node --test "tests/bench/*.test.js"` |
| Coverage gate | the whole suite, measured over `src/` | at least 99.9 % of lines, 99 % of functions and 93 % of branches of `src/` run under the suite (NFR-03); below any of the three the run fails. CI runs it in place of `npm test` on the required leg Ubuntu × Node 24, so a pull request below the bar does not merge | `npm run test:coverage`: the thresholds are in that script, and `tests/_coverage-bar.js` checks them to the decimal (Node's own threshold flags read whole numbers only, so 99.9 would act as 99) |

## The acceptance scenarios

The runner parses every feature file with the Gherkin reference parser and runs each scenario — each example of a Scenario Outline separately — as one test. Each step must match exactly one step definition. A scenario that does not run as written offline has one file of its own under `tests/acceptance/pending/`, named `<feature-stem>--<scenario-slug>.json`, with one of five classes (`conditional`, `external`, `forge`, `gap`, `model`) and a sentence of reason; it is reported as skipped and counted. A `conditional` scenario runs wherever its probe module `tests/acceptance/steps/_<needs>.js` finds what it needs; a `gap` names in `closes_in` the change that makes it run. There is no `drift` class: a scenario whose text disagrees with the specification is rewritten. The runner itself checks that every pending file is well formed and names a scenario, that no phrase has two definitions, that every scenario that runs has a definition for each step, and that every persona step definition is used; the shared phrases of `tests/acceptance/steps/_common.js` are exercised by `tests/acceptance/common-steps.test.js`.

The persona files are written to the command line as `agsc <verb> --help` states it, and a pending file never has the class `drift`. A scenario whose journey needs a forge or an outside service is split: the half that runs on the machine — a commit with its trailers, a publish served on loopback, the permissions read from a workflow file — is a scenario of its own that runs, and only the half that really needs the forge (`forge`), a model adapter (`model`) or an outside service (`external`) stays pending. A `gap` scenario shows a rule the reference engine does not meet yet; its steps are written and were seen failing for the reason its file states, and the change it names deletes the file when the scenario passes. A `conditional` scenario runs wherever what its `needs` names is present on the machine — the port implementer's comparison with the Python checker package (`python-package`: that package's checkout beside the engine and Python 3.9 or newer), and the restore from a bare clone of the patterns node (`real-bundles`: `AGSC_E2E=1` and that checkout, as for the real-Bundle lane below) — and is reported as skipped, with the reason, elsewhere. Every step that runs offline does so under a preload that refuses every network call, so a scenario that passes also proves that its lane reached no network and no model service.

## The rule-coverage matrix

`node tools/rule-coverage` reads the rules of `spec/*.md` and, for each active rule, the checks that name it:

- a live conformance vector whose `rule` member is the rule (a withdrawn vector counts for nothing);
- a test whose title carries the rule id, or any file under `tests/` that carries a marker comment `// verifies AGSC-nn-nn, AGSC-nn-nn` — the marker states that the assertions of that file check those rules;
- an acceptance scenario that is executed, whose tags or steps carry the id;
- the header comment of a checker under `tools/validate-*`.

A rule no check names must be listed in `tests/rule-coverage.allow.json`, either under `rules` as prose-only — with one of the reasons `definition`, `scope`, `pointer`, `person`, `forge`, `deferred` or `adapter` and a sentence — or under `gaps`, with what the engine does not do yet. An allow entry for a rule that is in fact verified is an error, so the list stays short. `node tools/rule-coverage --write` regenerates the page; `--check` (run by the suite and by CI) fails when the page is stale; `--json` prints the whole matrix.

The page also reports a tier that gates nothing: a verified rule is verified end to end when a live conformance vector, an executed acceptance scenario, a step file of the acceptance runner or a test under `tests/e2e/` names it. It lists the rules that state a requirement with MUST, MUST NOT, REQUIRED or SHALL and name a code but rest on unit, integration, architecture or checker-header evidence only, so a new conformance case or walk can be aimed at them.

`node tools/requirements-matrix` does the same for the requirements of `docs/PRD.md`, and writes [`docs/REQUIREMENTS-MATRIX.md`](REQUIREMENTS-MATRIX.md). A requirement that a rule traces to, or that a test or a live vector names, is mapped. One that is met only in part is listed under `partly` in `tests/requirements-matrix.allow.json`, with a reason from the closed list and a sentence naming the part that waits; a requirement whose rules carry no check at all must be listed there. A requirement measured by a command names, under `measured`, its `package.json` script and the test that asserts the script runs where it must (the coverage bar: `npm run test:coverage`, asserted by `tests/standard/workflow.test.js`).

## Optional lanes

- **Real Bundles.** `AGSC_E2E=1 npm run test:e2e` copies the patterns node and the Bundle the main site hands the engine (by default from the sibling checkouts `../AgenticSystemCore-Patterns` and `../AgenticSystemCore.com/dist/engine-bundle`; override with `AGSC_E2E_PATTERNS` and `AGSC_E2E_SITE`) and runs lint, build twice with a byte comparison, verify, `verify --ledger`, ci, `conform --level 2`, every export form and adapter, skills and compose, then the shipped checkers on the output. No draft may appear in any published file.
- **Browser.** `AGSC_BROWSER=1` with `CHROME_EXE` naming a Chromium or chrome-headless-shell binary and `playwright-core` resolvable (installed outside the repository with `npm i --no-save`, reached through `NODE_PATH`) serves the built fixture from 127.0.0.1 with its own Content-Security-Policy, and checks that the seven page tools register and answer through a stubbed `document.modelContext`, and that a page without it logs no error. In CI, the job `browser` of `test.yml` runs this lane on Ubuntu with a pinned `playwright-core` and a pinned `chrome-headless-shell`, each checked against its SHA-256; it fails if a browser test file skips, and it is not a check that branch protection requires.
- **SPARQL.** `AGSC_SPARQL_PYTHON=/tmp/sparql-env/bin/python node --test tests/knowledge/questions-sparql.test.js` (the environment: `python3 -m venv /tmp/sparql-env && /tmp/sparql-env/bin/pip install pyoxigraph==0.5.13`, outside the repository) loads the `graph.nq` of the ten-question fixture into Oxigraph, runs the SPARQL text of `docs/ontology-questions.json` and compares each result with the function of `src/knowledge/questions.js` and with the vectors `graph-0030` to `graph-0039` (AGSC-05-34). Without the variable the lane is skipped; the check that the text equals the specification always runs.

## Determinism

Every test fixes its clock (`SOURCE_DATE_EPOCH`, or fixed git author and committer dates), gives a spawned command an empty git identity and a scratch home, reaches no network — a local server binds 127.0.0.1 only — and writes only under the system temporary directory, removing what it wrote. The mode walks, the use cases and the documentation pages start every child process under the network trap of the acceptance scenarios (`tests/acceptance/steps/_offline.js`), which refuses and records every network call; a lane fails when a child reached for the network, even if the child caught the refusal. The suite gives the same result with and without `SOURCE_DATE_EPOCH` in the environment and under another time zone and locale.

## Three operating systems

`.github/workflows/test.yml` runs, on every pull request, every push to `main` or a `release/` branch and once a week (a newer push to a pull request cancels the run it supersedes), on Ubuntu, macOS and Windows and on Node 22.13.0 (the floor), 24 and 26, every step of the release gates of `release.yml` with the same wording and under the same condition: `npm ci`, lint, the duplicate check, the dependency rule, `npm test` (on Ubuntu × Node 24, `npm run test:coverage` in its place, with the coverage gate above), `npm audit`, the rule-coverage and requirements-matrix checks, the counting tool, every shipped checker, the discovery document of a fixture build at Levels 1 and 2, the packed install (both packages packed, the two tarballs installed together in an empty folder, and `agsc`, `agentic-system-core` and the alias each printing the packed version), the release lane's own checks (`tools/release --json`), the hygiene sweep and the architecture lane. The legs of Node 22.13.0 and 24 are the check contexts branch protection requires, and their names never change; the Node 26 legs are not required. `tests/standard/workflow.test.js` fails if the two workflows drift apart, if a required context is no longer produced, or if the coverage step, its thresholds or the packed install go missing. It runs with read-only permissions and actions pinned to commit hashes. Paths are joined with `path.join`, text files are LF on every checkout (`.gitattributes`), and the test scripts quote their globs for `cmd.exe`.

## For a second implementation

- The conformance vectors are language-neutral JSON; `tests/vectors/README.md` states their format, and a claim of a Level is a green run of that Level's set in any language.
- The persona scenarios in `features/` are plain Gherkin: write step definitions against your own command line, as `tests/acceptance/steps/` does against this one, and use the files of `tests/acceptance/pending/` as the list of what the scenarios cannot yet show offline.
- `tests/standard/` reads only the specification, the schemas, the vectors and a build output, so its checks apply to any writer's output.
- `tests/e2e/level-0-without-engine.test.js` shows the smallest Level-0 node, written by a few lines of code, passing the shipped checker.
