# Compliance crosswalk (informative)

*Written 2026-09-16 for the `1.0.0-rc.3` draft (DS-4); re-verified against `1.0.0-rc.4` on 2026-09-18. This is a map from external frameworks to the rules of this specification, for readers who must answer "does this help with X?". It is not legal advice, it creates no obligation, and most rows say "not applicable, and why". Three readings are used: **applies** (the framework imposes something on a publisher or implementer of this format), **helps** (a rule here supplies evidence a framework asks for), **not applicable** (with the reason).*

| Framework | Reading | Where this specification meets it | Note |
|---|---|---|---|
| **EU AI Act** (Regulation (EU) 2024/1689) | helps | `prov.origin ∈ human / ai-assisted / ai-generated / imported`, `prov.model`, `prov.operator` on every item (spec/08 §8.1); the derived ledger (§8.5) | The format is not an AI system and the reference engine runs no model on any gating lane. A publisher that enables an agent lane (AGSC-08-28, rc.4) deploys a model-driven process: the `agents[]` declaration (model, operator, budget), the Episode of every run and the ledger's `mode: auto` entries are the machine-readable record of that use, and the operator named in the declaration is the accountable person. Where a publisher generates items with a model, the provenance fields are the machine-readable record that Article 50-style transparency asks for; nothing here decides which obligations apply to a given publisher. |
| **NIST AI RMF 1.0** | helps | provenance contract, gates (§8.3), the four agent-safety lints (§8.4), untrusted marking of every model-bound text (AGSC-08-18, 11-11) | Supplies *Map* and *Measure* evidence for knowledge an agent consumes; governs nothing about the agent itself. |
| **ISO/IEC 42001:2023** (AI management systems) | not applicable | — | An organisational management standard; a file format cannot conform. Its documentation expectations are served by the same provenance fields. |
| **ISO/IEC 27001 / 27002** | not applicable | — | Organisational. The threat model (`docs/PLAN.md` §12, `docs/SECURITY-CONSIDERATIONS.md`) is the artefact an auditor would read. |
| **GDPR** (Regulation (EU) 2016/679) | applies to publishers | `prov.operator` and DCO-Plus trailers name people (`human:<name>`); the ledger is public and derived from git history; no analytics beacon or third-party script is ever emitted (AGSC-06-05); `site.analytics_token` is never emitted (AGSC-01-18) | A publisher chooses the identifiers it publishes and owns the lawful basis. The format collects nothing from readers: static pages, no cookies, no forms (D47). Right-to-erasure against an immutable ledger is a publisher decision the format neither prevents nor solves — a retirement (AGSC-11-22) removes an item from every export while keeping the IRI. **Added at rc.5 (V9A-23), stated so that no publisher meets it by surprise:** `prov.operator` is a published identifier of a natural person on **every** item — emitted as `asc:operator` by AGSC-05-26 into all four RDF views, defaulted by AGSC-02-90(2) from the local part of `git user.email`, and deliberately exempt from the `no-pii` lint by AGSC-08-16. The pseudonymisation path is to set `bundle.operator` to a role identifier (`human:editorial`) before `init`; after publication the format offers no removal other than a new item under AGSC-01-12. `docs/SECURITY-CONSIDERATIONS.md` §5 carries the same note. |
| **EU Data Act** (Regulation (EU) 2023/2854) | not applicable | — | Concerns data generated by connected products and cloud switching; a static publication is neither. |
| **Cyber Resilience Act** (Regulation (EU) 2024/2847) | mostly not applicable; helps | a minimal, pinned and audited dependency set with a committed lockfile, `npm ci` installs and a blocking `npm audit` gate (ADR-019, D94, 2026-09-18 — superseding the zero-dependency rule of ADR-002), attested releases (PRD-048), `security.txt` route (AGSC-06-01), the derived ledger | The reference engine is free and open-source software developed outside a commercial activity; a commercial redistributor inherits the obligations, and the artefacts above are the evidence it would start from. |
| **EU Copyright (DSM Directive 2019/790, Art. 4 TDM reservation)** | applies to publishers | TDMRep policy at `/.well-known/tdmrep.json`, robots signals, `schema:license`/`schema:usageInfo`, Content Use Terms in every prose export — one policy in three dialects, and the three comparable facts must agree or the build fails (AGSC-06-18 as amended at rc.5, V9A-07). Since rc.5 the identifier `LicenseRef-AgenticSystemCore-Content-Use-1.0` names FIXED TEXT: the `LICENSE-CONTENT` file whose SHA-256 is `b2e8da62e6a41886296d2d2358fb4642cc7418e806eb4a29ada12b588ac32857` (AGSC-06-18, V9A-24), so a rightholder or a crawler can verify that two nodes carrying the identifier carry the same terms, and a distribution with different wording must use a different identifier | The reservation is expressed machine-readably where the Directive expects it; aipref fields are deliberately not emitted at 1.x. |
| **Creative Commons / SPDX** | applies | `bundle.license_prose`, `bundle.license_schema`, `attachments[].license` as SPDX or `LicenseRef-` identifiers (AGSC-01-18, 02-98) | Schema, ontology and identifiers are CC0-1.0; prose is whatever the publisher declares under the Content Use Terms. |
| **REUSE 3.3** | applies to the repository | repository layout, not a route (AGSC-06-01 note) | An obligation of the 1.0.0 repository (no `LICENSES/` directory or `REUSE.toml` exists at rc.4 — AR2-59). |
| **SLSA v1.0** | helps | reproducible builds from four inputs (AGSC-04-01, 04-18), double-build verify (04-02), tag-triggered attested publishing (PRD-048) | Build L2-style evidence; the level a release reaches is stated in the release, never here. |
| **OWASP Top 10 for LLM Applications** | helps | LLM01 prompt injection: `injection-scan` over bodies, frontmatter at any depth, attachment text and every prose surface (AGSC-08-13); every model-bound text `untrusted` (08-18); peer prose `untrusted` with origin (11-11); tool annotation hints on WebMCP (11-18). LLM03/05 supply chain and output handling: pinned vectors, digests on every artefact, no remote tools served at 1.0 | Structural defence (ADR-001) with an honest limit: novel phrasing is not caught by a lint. |
| **WCAG 2.2 AA / EU Accessibility Act** | applies to sites; helps | `alt` REQUIRED on every attachment and diagram (AGSC-02-13, 02-98); pages proved in the PLAN §10 lane | The Act's scope depends on the publisher; the format makes the accessible path the only path. |
| **W3C PROV, SKOS, OWL 2 RL** | applies | spec/05 | The graph is a conforming PROV-O and SKOS instance by construction (AGSC-05-13…22). |
| **RFC 8615 / RFC 8288 / RFC 9264 / RFC 9530** | applies | spec/06 §6.2, spec/11 §11.2 | Two registrations are *requested* through the Internet-Draft (suffix, profile URI); the discovery link is the registered `describedby` (AGSC-06-25, D82). |
| **RFC 9309 robots.txt** | applies | AGSC-06-18 | `robots.txt` is one of the three dialects. What a build emits is one `User-agent: <token>` group with `Disallow: /` for each product token of `site.tdm_crawlers[]`, in configured order, when the node publishes a TDM reservation; then `User-agent: *` with `Allow: /` — assistants and search crawlers stay invited — a comment naming the policy, and a `Content-Signal` field (`search=yes, ai-input=yes, ai-train=no`). A node that publishes a reservation with an empty token list fails its build with `AGSC-E202`; vector `disc-0012`. *(Corrected 2026-09-23, EXT-2b: this row still said "no `Disallow` group", which AGSC-06-18 as amended at rc.6 (PSF-01) made false for every node that publishes a TDM reservation.)* *(Corrected 2026-09-21: this row read "no `Content-Signal` field is emitted (AR2-60)", which both of this project's own builds contradict — `src/distribution/site.js#robots` and the first site's generator have emitted the field since the route existed. `Content-Signal` is Cloudflare's Content Signals Policy, published at contentsignals.org on 2025-09-24 under CC0 and not a standard of any body. RFC 9309 defines `user-agent`, `allow` and `disallow` only, and its §2.2.4 says "Crawlers MAY interpret other records that are not part of the robots.txt protocol", so the field is an extension record a crawler may ignore — which is why AGSC-06-18 says of the RFC 9309 rules "These rules are not a form of access authorization". AGSC-06-18 names `rsl.xml` and the AIPREF `Content-Usage` field as not emitted at 1.x; it neither requires nor forbids `Content-Signal`, so the emission conforms and this row, not the writer, was wrong.)* |

**How to use this page.** Find the framework, read the reading, follow the rule id into `spec/`. If a row is wrong, the fix is a Proposal against this file — it is informative and carries no rule.
